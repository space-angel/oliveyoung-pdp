# oliveyoung-pdp

리뷰 25,000건에서 **구매 결정에 쓰이는 질문–답 쌍**을 만든다.
AI 가 요약하는 파이프라인이 아니라, **AI 가 말해도 되는 조건을 먼저 설계한** 파이프라인이다.

```json
{
  "question": "복합성인데 이거 하나로 속건조까지 잡힐까?",
  "verdict":  "속보습감은 좋다는 평이 많지만, 덜 느껴진다는 말도 있다",
  "condition": {"skinType": ["A03"]},
  "direction": "mixed",
  "support": {"positiveAuthors": 47, "negativeAuthors": 3,
              "spokeAuthors": 50, "silentAuthors": 45, "cellAuthors": 95},
  "evidence": [{"reviewId": 38875488, "quote": "원문 그대로", "stance": "negative"}]
}
```

> `main` 은 **실행 경로만** 둔다. 측정 스크립트·리포트 128개·골든셋·결정 문서·v4 기준선은
> `archive` 브랜치에 있다 — `git checkout archive -- eval/ docs/`.
> 아래 수치의 근거 파일은 전부 그쪽에 있고, 경로를 함께 적었다.

---

## 1. 왜 요약이 아닌가

올리브영 PDP 에는 **만족도 요약이 이미 있다.** *"건성 87명 중 72명이 보습력 만족"* 같은 것.
거기에 AI 요약 카드를 하나 더 얹는 건 새 정보가 아니다.

인터뷰한 여덟 명 중 일곱 명이 **이미 구체적인 고민을 갖고** 리뷰탭에 들어왔다.
*"건성인데 속당김 없나요?"* 그 답을 찾으려면 리뷰 수백 개를 직접 읽어야 한다.

그래서 이 파이프라인이 주는 건 비율이 아니다. **무엇이 만족과 불만을 갈랐는가**다.
사람들이 유튜브에 *"[제품명] 단점"* 을 검색하는 자리가 거기다.

```
❌ "말한 사람 중에서는 커버력이 좋다는 평가가 많다. 다만 아쉽다는 리뷰도 있다."
   → 읽어도 뭘 해야 할지 모른다. 그리고 만족도 요약이 이미 하는 말이다

⭕ "대체로 순하고 진정 효과까지 있지만, 광대 부위 좁쌀을 언급하는 소수도 있다"
   → 광대 부위 좁쌀. 이게 결정에 쓰인다
```

## 2. 1차 버전은 왜 올리지 않았나

이 프로젝트의 모든 통제는 **실패를 하나씩 맞고 그 자리에 박은 것**이다. 설계가 먼저가 아니었다.

### 리포트 맨 위에 "합격"이 떠 있었다

1차 평가 리포트의 `gate.pass` 는 `true` 였다. 합격 조건 6개가 전부 통과였으니까.
그 6개가 무엇이었냐면 — **제품이 5개인가 · 질문이 3~7개인가 · 근거 ID 가 5개 이상인가 ·
ID 가 실재하는가 · 질문이 물음표로 끝나는가 · 카테고리가 어휘 안인가.**

전부 **형식 검사**다. 같은 리포트가 계산해놓고 **합격 산식에는 안 넣은** 값이 이것들이었다.

| 실제로 잰 것 | 결과 | 산식에 |
|---|---|---|
| 인용 정확도 | **127 / 143 = 88.8%** | ❌ |
| 제품당 카테고리 3종 이상 | **1 / 5** | ❌ |
| 리스크 질문이 있는 제품 | **3 / 5** | ❌ |

> **"질문이 물음표로 끝나는가"는 합격 조건이었고, "인용이 원문에 있는가"는 아니었다.**

모델의 실패가 아니라 **평가 설계의 실패**다. 재기 쉬운 것으로 기준을 채운 결과다.
*근거: `archive:eval/reports/eval_report_v4.json`*

### 인용 16건이 원문에 없었다

88.8% 의 나머지를 열어봤다.

```
14시간 넘게 있는데 수정화장 안함        피부에 나타나던 트러블들이 눈에 띄게 옅어짐
향은 거의 없어 부담 없음                무향이라 자극많은 피부에 잘 맞음
```

**16건 중 8건이 명사형으로 끝난다** — `옅어짐` `없음` `맞음` `안함` `무너짐`.
사람은 리뷰를 이렇게 쓰지 않는다. **요약하는 쪽의 말투**다. 그리고 `14시간` 은 원문에 없다.

16건을 **원본 25,000건 전체에** 다시 대조했다(보이지 않는 문자만 접고). **0건 일치.**
잘못된 리뷰에 붙인 게 아니라 **문장 자체가 존재하지 않는다.**

비용의 성격이 여기서 갈린다.

- 정보를 **놓치면** → 리뷰를 더 읽으면 된다. 회복 가능
- 없는 사실을 **믿으면** → 잘못된 결정을 하고 되돌릴 수 없다

그리고 결정적으로, **이 실패는 에러를 내지 않는다.** 파이프라인은 정상 종료하고 초록불이 켜진다.

## 3. 그래서 무엇을 바꿨나 — 프롬프트가 아니라 파이프라인

### 인용을 사후 지표에서 **생성 게이트**로

```python
# claim_contract.py
if not self.evidence:
    raise ClaimContractError(...)   # 근거 없이 문장이 만들어지지 않는다
```

원문 부분문자열이 아니면 **그 claim 을 내지 않는다.** 검증에서 걸러내는 게 아니라 생성자가 막는다.
현재 인용 정확도 **100% (938/938)** 는 측정해서 올린 수치가 아니라 **구조상 다른 값이 나올 수 없는** 것이다.

대조할 때는 **보이지 않는 문자만 접는다.** 원문에 CRLF 46.3%, 공백 변종 1.1% 가 섞여 있어
안 접으면 정상 인용이 탈락한다. **공백 전체 squeeze 는 금지** — 띄어쓰기를 지운 편집까지 통과시킨다.

### "내 피부에 맞나" 질문이 5제품 중 4개에서 0개였던 이유

처음엔 프롬프트를 의심했다. *"적합성 질문도 만들어라"* 를 더 세게 쓰면 될 줄 알았다.

원인은 **데이터에 축이 하나 빠져 있던 것**이었다. 피부타입을 코드가 아니라 **문자열 라벨**
(`"건성"`)로 받다가 중간 단계에서 누락됐고, 집계에서 안 합쳐지니 조건 셀이 아예 안 만들어졌다.

**없는 축으로는 가를 수 없다.** 프롬프트를 아무리 고쳐도 안 나온다.
지금은 조건이 코드북(26종) 도메인 안의 코드여야 하고, **밖의 값은 조용히 새 세그먼트가 되지
않고 에러다.** *근거: `archive:docs/DECISION_PER176_*`*

### 세는 단위

| 실측 | |
|---|---|
| 리뷰 40건 중 같은 사람이 재구매하며 또 쓴 것 | **22.4%** |
| 작성자 게이트를 안 걸었을 때 카운트 부풀림 | 코퍼스의 **19.7%** |
| 본문 해시(중복 텍스트)로 잡히는 비율 | 그중 **12.1%뿐** |
| 한 리뷰 안에서 방향이 갈리는 비율 | **20.5%** |
| 별점과 태그 방향이 불일치하는 비율 | **12.9%** |

*"발색은 예쁜데 지속력은 별로예요"* 는 별점 5점이다.
**별점을 방향의 대리값으로 쓰면 8건 중 1건이 반대로 세어진다.**

그래서 집계 단위를 **고유 작성자 수**로, 태그 단위를 **(리뷰 × aspect)** 로 쪼갰다.

### 버린 것을 남긴다

```
원장 12,597행   리뷰 7,328 · 주장 5,269   전부 사유와 수치가 붙는다
```

컷은 삭제가 아니라 `rejected[]` 행이다. **통과한 것만 채점하면 정밀도는 재도 재현율은 영영
못 잰다.** 이게 이 프로젝트에서 값을 가장 많이 돌려준 결정이다 — 4절에서 이어진다.

## 4. mixed 를 어떻게 판단하는가

화장품 리뷰는 한쪽으로 쏠리는 경우가 드물다. 현재 산출물 **236건 중 210건이 mixed** 다.
그래서 "갈렸다"를 어떻게 다루느냐가 이 파이프라인의 핵심이 됐다.

### 비율이 아니라 존재로 정한다

긍정 작성자와 부정 작성자가 둘 다 있으면 mixed 다. **반대가 1명이어도 예외가 아니다.**

> 소수 의견을 다수로 뭉개는 순간, **그 정책이 옳았는지 영영 측정할 수 없다.**

대신 `single_dissent` 한계로 남긴다. 컷이 아니다.

### 같은 mixed 도 다 같지 않다 — 판정을 바꾸지 않고 주석을 단다

`부정 3 / 긍정 94` 와 `부정 29 / 긍정 62` 는 같은 판정이지만 다른 상황이다.
앞의 것은 **태거가 방향을 뒤집은 것만으로 설명된다.**

귀무가설을 세운다 — *"이 묶음은 사실 전부 다수 방향이고 소수는 태거가 뒤집은 것이다."*
관측 확률이 `NOISE_ALPHA` 미만이면 `minority_beyond_noise`, 아니면 판정은 **그대로 mixed** 이고
`minority_within_tagger_noise` 한계가 붙는다. 문턱이 표본 크기를 따라 움직이는 게 요점이다 —
고정 비율(20%)은 n=8 에서 헐겁고 n=400 에서 빡빡하다.

```
n=  8  소수 2건 이상 (25.0%)      n=100  소수  7건 이상 ( 7.0%)
n= 50  소수 5건 이상 (10.0%)      n=400  소수 20건 이상 ( 5.0%)
```

### 인용 상한이 방향을 통째로 지우지 않는다

여기서 실측 하나가 설계를 바꿨다.

> `p019 × 트러블/자극` 은 **긍정 309명 · 부정 6명**인데,
> 신뢰도 상위 8건이 **전부 긍정**이었다.

그대로 자르면 *"부정 6명"* 이라고 수는 적혀 있는데 **생성기가 인용할 반대 근거가 화면에서
사라진다.** 그래서 **정렬과 선별을 분리**했다 — 정렬 규칙은 `trust.rank_key()` 하나뿐이고,
상한 때문에 한 줄도 안 남은 방향이 있으면 그 방향 **1위를 자리 배정**하고 최다 방향의
최하위를 뺀다. 승격된 인용도 **원래 순위를 그대로 달고** 나간다.

컷이 아니라 자리 배정이다. *근거: `archive:eval/reports/context_layout_per187.json`*

### 침묵은 근거가 아니다

| | 비율의 분모인가 |
|---|---|
| 긍정·부정을 **명시한** 작성자 | ✅ |
| 언급은 했지만 방향이 없음 (`"지속력은 보통"`) | ❌ |
| 그 주제를 아예 말하지 않음 | ❌ |

전수에서 태그가 0개인 리뷰가 **5,443건**이다. 분모에 섞으면 모든 비율이 조용히 희석된다.
*"355명 중 12명만 향을 말했는데 대부분 문제 없다"* 는 **343명의 침묵을 긍정으로 센 것**이다.

## 5. 무엇과 비교했는가 — 정답지를 먼저 만들었다

수치를 말하기 전에 기준이 있어야 한다. **골든셋을 생성기보다 먼저 만들었다.**

```
번들 40개 · 리뷰 1,267건        라벨러가 읽는 분량
지금까지 5번들 146리뷰 → 정답 claim 26건 · 119분
```

**라벨러는 리뷰 번들만 본다.** 파이프라인이 무엇을 냈는지 모르는 채로 질문·답·근거 인용을
직접 쓴다 — 모델이 정답을 정하면 **자기 답안으로 자기를 채점**하는 게 된다.

| 설계 | 왜 |
|---|---|
| 별점 층화 (1–2점 12 · 3점 8 · 4점 8 · 5점 12) | 5점 쏠림을 두면 불만 사례를 못 본다 |
| 번들 종류 할당 (제품 16 · 피부타입 10 · 옵션 6 · 고민 4 · **미기재 4**) | 조건부 주장을 구조적으로 강제. 미기재 셀은 *"미기재 ≠ 조건 없음"* 을 라벨에서 검증 |
| 셀 최소 8명 = 게이트4 `N_min` | 평가 기준과 운영 기준을 따로 두면 비교가 안 된다 |
| `source` 4종 + `candidateId` | 후보 모델이 어디서 틀렸는지 남는다. **후보를 버린 것도 기록** |
| `direction` 은 사람이 고르지 않고 **계산** | 사람의 인상이 들어갈 자리를 없앤다 |

### 재생성 금지의 직접 원인

태깅 정답셋을 v1 → v2 로 재라벨했다. 같은 표본, 같은 사람, 규격만 정비했는데 —

| | 태그 |
|---|---:|
| v1 | 365 |
| v2 | 432 |
| **뺀 것** | **49** |
| **더한 것** | **116** |
| 방향이 바뀐 것 | 8 |

**165건이 움직였다.** 문제는 숫자가 아니다.
**v1 기준으로 잰 모든 점수가 v2 가 나온 순간 비교 불가능해진다.**
모델이 좋아진 건지 정답지가 바뀐 건지 구분할 방법이 없다.

그래서 `eval/gold/` 는 **재생성되지 않는 고정물**이고, 병합 게이트에 `--check` 가 들어 있고,
변화를 **치명**(리뷰 집합이 바뀜 → 그 번들 라벨 무효) / **양성**(파생 필드만)으로 가른다.
그리고 v1→v2 차이를 **165건 전부 목록으로** 남겼다 — *"이 표의 어느 줄도 자동으로 채택되지 않는다."*

### 결과

```
되짚을 수 있는 정답 22건 중 16건 → 재현율 0.7273
못 낸 6건은 전부 같은 사유 — 근거 부족(게이트4)
택소노미 밖 aspect 4건은 분모에서 뺐다
```

**못 낸 6건이 전부 같은 사유였다는 게 이 프로젝트의 수확이다.**
흩어진 버그면 고칠 방법이 없는데, **임계값 하나를 조정할 문제**라는 걸 알아냈다.
원장이 없었으면 프롬프트만 계속 다듬고 있었을 거다.

택소노미 밖 4건을 분모에서 뺀 것도 적는다. 안 빼면 재현율이 **조용히 올라간다.**

## 7. 아직 못 갚은 것

같은 기준으로 우리 자신도 봐야 하니 적는다.

- **번들마다 사람이 백지에서 쓴 라벨(`source = human`) 1건 이상** 규칙이 **5번들 중 1개만 충족**이다.
  나머지는 후보를 사람이 검수·수정한 것이라, 후보 모델의 사고 틀이 정답지에 새어 들어갔을
  가능성을 배제할 수 없다. 다음 라벨링 회차의 선행 조건.
- 골든셋 **26건 / 목표 100건**.
- 조건별 방향 갈림은 **파이프라인 실제 입력에서 우연과 구별되지 않았다.**
  게이트 이전 전건에서는 유의해 보이던 쌍이 117개였는데(순열 p=0.0),
  중복 게이트만 걸어도 34개, 실제 입력(동일성+중복)에서는 **19개 · 순열 p=0.495** 다.
  다중비교 보정 후에는 Bonferroni·Holm 모두 **0건**. 조건축이 유효하다고 말할 수 없고,
  **중복 작성자가 만든 착시였다**는 것까지 그대로 적어뒀다.
  *근거: `archive:eval/reports/condition_split_per192.json`*
- `judge`(자동 평가) 단계는 미구현.

## 8. 돌려보기

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # ANTHROPIC_API_KEY

URL="https://www.oliveyoung.co.kr/store/goods/getGoodsDetail.do?goodsNo=A000000211119"
.venv/bin/python pipeline/run_url.py --url "$URL" --check   # 계획과 비용만
.venv/bin/python pipeline/run_url.py --url "$URL" --yes     # 실제로
```

`crawl → catalog → ingest → tag → gates → claims → report`.
산출물은 `data/runs/<runId>/claims.jsonl`.

| | |
|---|---|
| **비용** | `crawl` 은 실제 요청, `tag` ~$0.1/500건, `claims` ~$1~2/제품. `--yes` 없이는 안 돈다 |
| **격리** | 전부 `data/runs/<runId>/` 안. `assert_isolated()` 가 **크롤 전에** 정본을 안 건드리는지 검사한다 |
| **카탈로그** | 수집분에서 만든다. 변형 SKU(제품당 평균 4종)를 빠뜨리면 입수가 미등록 `goodsNo` 로 멈춘다 |
| **재현율** | **재지 않는다.** 새 제품에는 정답지가 없다 — `run.json` 에 사유가 적힌다 |

마지막 줄이 이 프로젝트의 태도다. 못 잰 것을 안 적으면 *"안 나왔다"* 와 *"나빴다"* 를
구분할 수 없다. **v4 가 떨어진 검사 둘을 합격 산식에서 빼놓고 "합격"을 띄운 것과 같은 실패다.**

### 구조

```
pipeline/
  run_url.py         링크 하나로 끝까지 — 진입점
  workspace.py       경로 배치. canonical() 과 for_run() 두 종류뿐
  contracts.py       입력 계약 3층 (원문/조건/파생)
  catalog.py         goodsNo → productId. 미등록은 에러
  codebook.py        조건 어휘 26종. 도메인 밖은 에러
  policy.py          리센시 · 리뉴얼 · 충분성 임계값
  ingest.py          수집분 → v5 레코드 (LLM 없음, 재실행 일치)
  tag.py             (리뷰 × aspect) 태깅 — 배치 API
  trust.py           신뢰도 사전 점수. 필터가 아니라 가중치
  gates.py           게이트1 동일성 · 게이트2 중복
  polarity.py        게이트3 방향성 — 유일하게 탈락시키지 않는 게이트
  sufficiency.py     게이트4 충분성 — U ≥ N AND U/D ≥ R AND S ≥ S
  ledger.py          통합 rejected[] 원장
  context_layout.py  5단 배치. 상한이 방향을 통째로 지우지 않는다
  generate.py        claim 생성기
  quote_gate.py      인용 원문성 — 생성 게이트
  test_*.py          계약 테스트 (683건)
crawler/             올리브영 cursor API 크롤러
```

**AI 는 가운데 두 칸만 맡는다** — 문장을 읽고(`tag`) 쓰는(`claims`) 자리.
앞뒤는 규칙이다. 같은 걸 넣으면 같은 게 나와야 하는 자리이기 때문이고,
자율 에이전트가 아니라 순서가 고정된 파이프라인이라 **어느 단계에서 어긋났는지 찾을 수 있다.**
