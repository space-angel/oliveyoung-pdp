# oliveyoung-pdp

올리브영 제품 상세 페이지(PDP, Product Detail Page)의 리뷰 25,000건에서 **구매 결정에 쓰이는 질문–답 쌍**을 만들어요.

AI 가 리뷰를 요약하는 파이프라인이 아니에요. **AI 가 말해도 되는 조건을 먼저 설계한** 파이프라인이에요. 근거가 없으면 문장 자체가 만들어지지 않고, 버려진 근거는 사유와 함께 원장에 남아요.

이 문서는 그 조건을 하나씩 설명해요. 조건은 설계에서 나온 게 아니에요. 1차 버전(v4)의 실패를 하나씩 맞고 그 자리에 박은 거예요. 그래서 2절부터는 **증상 → 원인 → 조치 → 근거 파일** 순서로 씁니다.

| 알고 싶은 것 | 절 |
|---|---|
| 무엇이 나오나요 | 산출물 |
| 왜 요약이 아닌가요 | 1절 |
| 무엇이 실패했고 무엇으로 바꿨나요 | 2절, 3절 |
| 갈린 의견을 어떻게 판정하나요 | 4절 |
| 무엇과 비교해서 잰 수치인가요 | 5절, 6절 |
| 무엇을 아직 못 했나요 | 7절 |
| 직접 돌려보려면요 | 8절 |

## 산출물

파이프라인이 내보내는 단위는 claim 하나예요. 질문, 답, 답이 성립하는 조건, 원문 인용을 한 덩어리로 묶어요.

```json
{
  "question": "복합성인데 이거 하나로 속건조까지 잡힐까?",
  "verdict":  "속보습감은 좋다는 평이 많지만, 덜 느껴진다는 말도 있다",
  "condition": {"skinType": ["A03"]},
  "direction": "mixed",
  "support": {"positiveAuthors": 47, "negativeAuthors": 3,
              "spokeAuthors": 50, "silentAuthors": 45, "cellAuthors": 95},
  "evidence": [{"reviewId": 38875488, "quote": "원문 그대로", "stance": "negative"}]
}
```

| 필드 | 무엇인가요 | 어떤 통제를 받나요 |
|---|---|---|
| `question` | 리뷰탭에 들어온 사람이 실제로 가진 고민 | 4축(적합성·리스크·맥락·비교) 중 하나에 속해요 |
| `verdict` | 그 고민에 대한 답 | 비율이 아니라 무엇이 만족과 불만을 갈랐는지를 써요 |
| `condition` | 이 답이 성립하는 조건 (`A03` = 복합성) | 코드북 26종 안의 코드만 허용해요. 밖의 값은 에러예요 |
| `direction` | 방향 판정 | 사람이 고르지 않고 계산해요 (4절) |
| `positiveAuthors` / `negativeAuthors` | 방향을 명시한 고유 작성자 수 | 리뷰 수가 아니라 사람 수예요 (3-3절) |
| `spokeAuthors` | 이 주제를 말한 작성자 수 (47 + 3) | 비율의 분모는 이 값이에요 |
| `silentAuthors` | 셀 안에 있지만 이 주제를 말하지 않은 작성자 수 | 분모에 넣지 않아요 (4-4절) |
| `cellAuthors` | 조건 셀 전체 작성자 수 (50 + 45) | 셀 크기를 드러내려고 함께 실어요 |
| `evidence[].quote` | 원문 그대로의 인용 | 원문 부분문자열이 아니면 claim 이 생성되지 않아요 (3-1절) |
| `evidence[].stance` | 인용이 받치는 방향 | 인용 상한이 한 방향을 통째로 지우지 않아요 (4-3절) |

## 1. 요약이 아니라 무엇이 갈랐는지를 보여줘요

올리브영 PDP 에는 만족도 요약이 이미 있어요. "건성 87명 중 72명이 보습력 만족" 같은 거예요. 거기에 AI 요약 카드를 하나 더 얹으면 새 정보가 아니에요.

인터뷰한 여덟 명 중 일곱 명이 이미 구체적인 고민을 갖고 리뷰탭에 들어왔어요. "건성인데 속당김 없나요?" 그 답을 찾으려면 리뷰 수백 개를 직접 읽어야 해요.

그래서 이 파이프라인이 내는 건 비율이 아니에요. **무엇이 만족과 불만을 갈랐는가**예요. 사람들이 유튜브에 "[제품명] 단점"을 검색하는 자리가 거기거든요.

| | 문장 | 왜 그런가요 |
|---|---|---|
| ❌ | "말한 사람 중에서는 커버력이 좋다는 평가가 많다. 다만 아쉽다는 리뷰도 있다." | 읽어도 무엇을 해야 할지 모르겠어요. 만족도 요약이 이미 하는 말이기도 해요 |
| ⭕ | "대체로 순하고 진정 효과까지 있지만, 광대 부위 좁쌀을 언급하는 소수도 있다" | "광대 부위 좁쌀"이 결정에 쓰여요 |

## 2. 1차 버전은 형식 검사만 통과하고 합격했어요

### 2-1. 합격 조건 6개가 전부 형식 검사였어요

1차 평가 리포트의 `gate.pass` 는 `true` 였어요. 합격 조건 6개를 전부 통과했거든요. 조건은 이랬어요.

- 제품이 5개인가
- 질문이 3~7개인가
- 근거 ID 가 5개 이상인가
- ID 가 실재하는가
- 질문이 물음표로 끝나는가
- 카테고리가 어휘 안인가

전부 형식 검사예요. 같은 리포트가 계산해놓고 합격 산식에는 넣지 않은 값이 따로 있었어요.

| 실제로 잰 것 | 결과 | 합격 산식에 |
|---|---|---|
| 인용 정확도 | 127 / 143 = 88.8% | ❌ |
| 제품당 카테고리 3종 이상 | 1 / 5 | ❌ |
| 리스크 질문이 있는 제품 | 3 / 5 | ❌ |

"질문이 물음표로 끝나는가"는 합격 조건이었는데, "인용이 원문에 있는가"는 아니었어요.

모델의 실패가 아니라 평가 설계의 실패예요. 재기 쉬운 항목으로 기준을 채운 결과거든요.

근거: `archive:eval/reports/eval_report_v4.json`

### 2-2. 인용 16건이 원문에 없었어요

88.8% 의 나머지 16건을 열어봤어요.

```
14시간 넘게 있는데 수정화장 안함        피부에 나타나던 트러블들이 눈에 띄게 옅어짐
향은 거의 없어 부담 없음                무향이라 자극많은 피부에 잘 맞음
```

16건 중 8건이 명사형으로 끝나요. 옅어짐, 없음, 맞음, 안함, 무너짐. 사람은 리뷰를 이렇게 쓰지 않아요. 요약하는 쪽의 말투예요. 그리고 "14시간"은 원문에 없는 숫자예요.

16건을 원본 25,000건 전체에 다시 대조했어요. 보이지 않는 문자만 접고 비교했을 때 일치한 문장은 **0건**이에요. 잘못된 리뷰에 붙인 게 아니라, 문장 자체가 존재하지 않아요.

여기서 비용의 성격이 갈려요.

- 정보를 놓치면 → 리뷰를 더 읽으면 돼요. 회복할 수 있어요
- 없는 사실을 믿으면 → 잘못된 결정을 하고 되돌릴 수 없어요

그리고 결정적으로, 이 실패는 에러를 내지 않아요. 파이프라인은 정상 종료하고 리포트에는 합격이 떠요.

## 3. 통제를 프롬프트가 아니라 파이프라인에 넣었어요

### 3-1. 인용을 사후 지표에서 생성 게이트로 옮겼어요

```python
# claim_contract.py
if not self.evidence:
    raise ClaimContractError(...)   # 근거 없이 문장이 만들어지지 않는다
```

원문 부분문자열이 아니면 그 claim 을 내보내지 않아요. 검증 단계에서 걸러내는 게 아니라 생성 단계에서 막아요. 그래서 지금의 인용 정확도 100%(938 / 938)는 측정해서 끌어올린 수치가 아니에요. 구조상 다른 값이 나올 수 없는 수치예요.

대조할 때는 보이지 않는 문자만 접어요. 원문에 CRLF 가 46.3%, 공백 변종이 1.1% 섞여 있어서 접지 않으면 정상 인용이 탈락하거든요. 다만 공백 전체를 squeeze 하는 방식은 금지예요. 띄어쓰기를 지운 편집까지 통과시키니까요.

### 3-2. 없는 축으로는 가를 수 없어요

"내 피부에 맞나" 질문이 5제품 중 4개에서 0개였어요. 처음에는 프롬프트를 의심했어요. "적합성 질문도 만들어라"를 더 세게 쓰면 될 줄 알았거든요.

원인은 데이터에 축이 하나 빠져 있던 거였어요. 피부타입을 코드가 아니라 문자열 라벨("건성")로 받다가 중간 단계에서 누락됐고, 집계에서 합쳐지지 않으니 조건 셀이 아예 만들어지지 않았어요.

없는 축으로는 가를 수 없어요. 프롬프트를 아무리 고쳐도 나오지 않아요. 지금은 조건이 코드북(26종) 도메인 안의 코드여야 하고, 도메인 밖의 값은 조용히 새 세그먼트가 되지 않고 에러가 돼요.

근거: `archive:docs/DECISION_PER176_*`

### 3-3. 세는 단위를 리뷰에서 사람으로 바꿨어요

| 측정 항목 | 값 |
|---|---|
| 표본 리뷰 40건 중 같은 작성자가 재구매하며 다시 쓴 리뷰 | 22.4% |
| 작성자 게이트를 걸지 않았을 때의 카운트 부풀림 | 코퍼스의 19.7% |
| 그 부풀림 중 본문 해시(중복 텍스트)로 잡히는 몫 | 12.1% |
| 한 리뷰 안에서 방향이 갈리는 비율 | 20.5% |
| 별점과 태그 방향이 불일치하는 비율 | 12.9% |

"발색은 예쁜데 지속력은 별로예요"는 별점 5점이에요. 별점을 방향의 대리값으로 쓰면 8건 중 1건이 반대로 세어져요.

그래서 집계 단위를 고유 작성자 수로 바꾸고, 태그 단위를 (리뷰 × aspect) 로 쪼갰어요.

### 3-4. 버린 근거를 남겨요

```
원장 12,597행   리뷰 7,328 · claim 5,269   전부 사유와 수치가 붙는다
```

컷은 삭제가 아니라 `rejected[]` 행이에요. 통과한 것만 채점하면 정밀도는 재도 재현율은 영영 재지 못해요. 이 프로젝트에서 값을 가장 많이 돌려준 결정이고, 5절에서 실제로 무엇을 돌려줬는지 이어집니다.

### 3-5. 근거가 부족하면 아예 만들지 않아요 (게이트4)

세 조건을 전부 만족해야 claim 을 내보내요.

```
U ≥ N_min  AND  U/D ≥ R_min  AND  S ≥ S_min
```

| 기호 | 인자 | 정의 |
|---|---|---|
| `U` | `support_authors` | claim 의 방향을 명시한 고유 작성자 수 |
| `D` | `spoke_authors` | 그 주제를 말한 고유 작성자 수 (중립 포함) |
| `S` | `cell_authors` | 셀의 유효 고유 작성자 수 (게이트2 통과분) |

| 임계값 | 값 | 뜻 |
|---|---|---|
| `N_min` | 8 | `U` 의 하한 |
| `R_min` | 0.1 | `U/D` 의 하한 |
| `S_min` | 8 | `S` 의 하한 |
| `minority_min` | 2 | 미만이면 `single_dissent` 한계를 붙여요 |

**판정 순서는 S → U → U/D 예요.** 셀이 말할 자격이 없으면(`S`) claim 의 근거 수(`U`)를 물을 이유가 없거든요. 그리고 탈락 사유가 하나로 정해져야 `rejected[]` 가 재현율의 단서가 돼요.

**`S ≥ S_min` 과 `U ≥ N_min` 은 값이 둘 다 8이지만 재는 대상이 달라요.** `S` 는 이 셀에 사람이 몇 명 있느냐고, `U` 는 그중 방향을 말한 사람이 몇 명이냐예요.

**불변식은 `U ≤ D ≤ S` 이고, 깨지면 에러예요.** 깨졌다는 건 말하지 않은 사람을 근거로 세었다는 뜻이니까요.

`S_min < N_min`, `R_min = 0`, `N_min = 0` 은 조건을 조용히 끄는 설정이라 에러로 막아뒀어요.

정의 원문은 `pipeline/policy.py` 의 `sufficiency_gate` 독스트링과 `SufficiencyPolicy` 에 있어요.

## 4. 갈린 의견은 비율이 아니라 존재로 판정해요

화장품 리뷰는 한쪽으로 쏠리는 경우가 드물어요. 현재 산출물 236건 중 210건이 mixed 예요. 그래서 "갈렸다"를 어떻게 다루느냐가 이 파이프라인의 핵심이 됐어요.

### 4-1. 긍정과 부정이 둘 다 있으면 mixed 예요

긍정 작성자와 부정 작성자가 둘 다 있으면 mixed 로 판정해요. 반대가 1명이어도 예외를 두지 않아요.

소수 의견을 다수로 뭉개는 순간, 그 정책이 옳았는지 영영 측정할 수 없거든요. 대신 `single_dissent` 한계로 남겨요. 컷이 아니에요.

### 4-2. 판정을 바꾸지 않고 주석을 달아요

부정 3 / 긍정 94 와 부정 29 / 긍정 62 는 같은 판정이지만 다른 상황이에요. 앞의 것은 태거가 방향을 뒤집은 것만으로도 설명되거든요.

그래서 귀무가설을 세워요. "이 묶음은 사실 전부 다수 방향이고, 소수는 태거가 뒤집은 것이다." 관측 확률이 `NOISE_ALPHA` 미만이면 `minority_beyond_noise` 를 붙이고, 아니면 판정은 그대로 mixed 로 두고 `minority_within_tagger_noise` 한계를 붙여요.

문턱이 표본 크기를 따라 움직이는 게 요점이에요. 고정 비율(20%)은 n=8 에서 헐겁고 n=400 에서 빡빡하거든요.

```
n=  8  소수 2건 이상 (25.0%)      n=100  소수  7건 이상 ( 7.0%)
n= 50  소수 5건 이상 (10.0%)      n=400  소수 20건 이상 ( 5.0%)
```

### 4-3. 인용 상한이 한 방향을 통째로 지우지 않아요

여기서 실측 하나가 설계를 바꿨어요.

p019 × 트러블/자극 은 긍정 309명, 부정 6명인데 신뢰도 상위 8건이 전부 긍정이었어요. 상한에서 그대로 자르면 "부정 6명"이라고 수는 적혀 있는데 생성기가 인용할 반대 근거는 화면에서 사라져요.

그래서 정렬과 선별을 분리했어요. 정렬 규칙은 `trust.rank_key()` 하나뿐이고, 상한 때문에 한 줄도 남지 않은 방향이 있으면 그 방향 1위를 자리에 배정하고 최다 방향의 최하위를 빼요. 승격된 인용도 원래 순위를 그대로 달고 나가요.

컷이 아니라 자리 배정이에요.

근거: `archive:eval/reports/context_layout_per187.json`

## 5. 정답지를 생성기보다 먼저 만들었어요

수치를 말하기 전에 기준이 있어야 해요. 그래서 골든셋을 생성기보다 먼저 만들었어요.

```
번들 40개 · 리뷰 1,267건        라벨러가 읽는 분량
지금까지 5번들 146리뷰 → 정답 claim 26건 · 119분
```

라벨러는 리뷰 번들만 봐요. 파이프라인이 무엇을 냈는지 모르는 채로 질문·답·근거 인용을 직접 써요. 모델이 정답을 정하면 자기 답안으로 자기를 채점하는 셈이 되니까요.

### 5-1. 이렇게 설계했어요

| 설계 결정 | 이유 |
|---|---|
| 별점 층화 (1–2점 12 · 3점 8 · 4점 8 · 5점 12) | 5점 쏠림을 그대로 두면 불만 사례를 보지 못해요 |
| 번들 종류 할당 (제품 16 · 피부타입 10 · 옵션 6 · 고민 4 · 미기재 4) | 조건부 claim 을 구조적으로 강제해요. 미기재 셀은 "미기재 ≠ 조건 없음"을 라벨에서 검증해요 |
| 셀 최소 8명 = 게이트4 `N_min` | 평가 기준과 운영 기준을 따로 두면 비교할 수 없어요 |
| `source` 4종 + `candidateId` | 후보 모델이 어디서 틀렸는지 남아요. 버린 후보도 기록해요 |
| `direction` 은 사람이 고르지 않고 계산 | 사람의 인상이 들어갈 자리를 없애요 |

### 5-2. 골든셋은 재생성하지 않아요

태깅 정답셋을 v1 에서 v2 로 재라벨했어요. 같은 표본, 같은 사람, 규격만 정비했는데 결과는 이랬어요.

| 항목 | 태그 수 |
|---|---|
| v1 | 365 |
| v2 | 432 |
| 뺀 것 | 49 |
| 더한 것 | 116 |
| 방향이 바뀐 것 | 8 |

165건이 움직였어요. 문제는 숫자가 아니에요. v1 기준으로 잰 모든 점수가 v2 가 나온 순간 비교 불가능해져요. 모델이 좋아진 건지 정답지가 바뀐 건지 구분할 방법이 없거든요.

그래서 `eval/gold/` 는 재생성되지 않는 고정물이고, 병합 게이트에 `--check` 를 넣었고, 변화를 둘로 갈라요.

- **치명**: 리뷰 집합이 바뀜 → 그 번들 라벨을 무효로 봐요
- **양성**: 파생 필드만 바뀜

그리고 v1 → v2 차이 165건을 전부 목록으로 남겼어요. 이 표의 어느 줄도 자동으로 채택되지 않아요.

### 5-3. 재현율은 72.7% 예요

- 되짚을 수 있는 정답 22건 중 16건을 냈어요. **72.7%** (16 / 22)
- 못 낸 6건은 전부 같은 사유예요. 근거 부족(게이트4)
- 택소노미 밖 aspect 4건은 분모에서 뺐어요

못 낸 6건이 전부 같은 사유였다는 게 이 프로젝트의 수확이에요. 흩어진 버그였다면 고칠 방법이 없는데, 임계값 하나를 조정할 문제라는 걸 알아냈거든요. 원장이 없었다면 프롬프트만 계속 다듬고 있었을 거예요.

택소노미 밖 4건을 분모에서 뺀 사실도 적어둡니다. 빼지 않으면 재현율이 조용히 올라가요.

## 7. 아직 갚지 못한 빚이 넷 있어요

같은 기준으로 저희 자신도 봐야 하니까 적어둡니다.

1. **라벨 독립성이 아직 부족해요.** 번들마다 사람이 백지에서 쓴 라벨(`source = human`) 1건 이상 규칙을 5번들 중 1개만 충족해요. 나머지는 후보를 사람이 검수·수정한 거라, 후보 모델의 사고 틀이 정답지에 새어 들어갔을 가능성을 배제할 수 없어요. 다음 라벨링 회차의 선행 조건이에요.
2. **골든셋이 26건이에요.** 목표는 100건이에요.
3. **조건축이 유효하다고 말할 수 없어요.** 조건별 방향 갈림은 파이프라인 실제 입력에서 우연과 구별되지 않았어요. 게이트 이전 전건에서는 유의해 보이던 쌍이 117개였는데(순열 p=0.0), 중복 게이트만 걸어도 34개, 실제 입력(동일성 + 중복)에서는 19개이고 순열 p=0.495 예요. 다중비교 보정 후에는 Bonferroni 와 Holm 모두 0건이고요. 중복 작성자가 만든 착시였다는 것까지 그대로 적어뒀어요. 근거: `archive:eval/reports/condition_split_per192.json`
4. **judge(자동 평가) 단계가 미구현이에요.**

## 8. 링크 하나로 파이프라인을 돌려요

### 사전 요구사항

- Python 3
- Anthropic API 키

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # ANTHROPIC_API_KEY 를 채워주세요
```

### 실행

```bash
URL="https://www.oliveyoung.co.kr/store/goods/getGoodsDetail.do?goodsNo=A000000211119"

.venv/bin/python pipeline/run_url.py --url "$URL" --check   # 계획과 비용만 출력해요
.venv/bin/python pipeline/run_url.py --url "$URL" --yes     # 실제로 실행해요
```

단계는 `crawl → catalog → ingest → tag → gates → claims → report` 순이에요. 산출물은 `data/runs/<runId>/claims.jsonl` 에 쌓여요.

### 알아두면 좋아요

| 항목 | 내용 |
|---|---|
| 비용 | `crawl` 은 실제 요청을 보내요. `tag` 는 리뷰 500건당 약 $0.1, `claims` 는 제품당 약 $1~2 예요. `--yes` 를 붙이지 않으면 돌지 않아요 |
| 격리 | 모든 산출물이 `data/runs/<runId>/` 안에 떨어져요. `assert_isolated()` 가 크롤 전에 정본을 건드리지 않는지 검사해요 |
| 카탈로그 | 수집분에서 만들어요. 변형 SKU(제품당 평균 4종)를 빠뜨리면 미등록 `goodsNo` 에서 입수가 멈춰요 |
| 재현율 | 재지 않아요. 새 제품에는 정답지가 없거든요. 이 사유가 `run.json` 에 적혀요 |

마지막 줄이 이 프로젝트의 태도예요. 못 잰 걸 적지 않으면 "안 나왔다"와 "나빴다"를 구분할 수 없어요. v4 가 떨어진 검사 둘을 합격 산식에서 빼놓고 합격을 띄운 것과 같은 실패거든요.
