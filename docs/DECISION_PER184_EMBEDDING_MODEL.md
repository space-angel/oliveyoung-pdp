## 1. 왜 로컬인가

**Anthropic API 에는 임베딩이 없다.** 외부 제공자(Voyage / OpenAI)를 쓰면 계정·키·비용·의존성이 추가되고, 무엇보다 **모델이 우리 통제 밖에서 바뀐다.** 로컬 모델은 revision 을 해시로 못박을 수 있어 PRD §5-2("같은 입력 → 같은 출력")에 유리하다. 25,000건 임베딩은 로컬 CPU 로도 감당 가능한 규모다.

## 2. 정답은 사람이 만든 것만 쓴다

probe 의 정답은 `eval/gold/v5_tags_pilot_gold.jsonl` 432행뿐이다. **전수 태그(`v5_tags.jsonl`, 38,251개)는 쓰지 않았다** — 그건 태거(LLM)의 산출물이고, 모델 산출물로 모델을 고르면 순환이다. 태거 재현율이 57.4%라 그걸 정답으로 삼으면 "태거를 잘 흉내내는 임베딩"을 고르게 된다.

## 3. 무엇을 재는가 — 키워드가 못 잡는 것을 잡는가

이 임베딩이 필요한 이유는 이슈 코멘트가 실측으로 적어 뒀다. *"단어를 더 넣어서 될 문제가 아니다."* 그래서 지표를 **키워드 기준선 대비**로 짰다.

정답 432행에 `eval/aspect_keywords.json` 을 그대로 걸어 본 결과:

| | 값 |
|---|--:|
| 정답 aspect 의 키워드가 스니펫에 **하나도 없는 행**(`blind`) | **174행 (40.28%)** |
| 키워드 argmax 분류 정답률 — 전체 | 56.25% |
| 　같은 지표 — 키워드가 보이는 행에서만 | 94.19% |
| 　같은 지표 — **`blind` 행에서** | **0.00%** |

**키워드는 보이면 거의 틀리지 않고(94.2%), 안 보이면 하나도 못 맞힌다(0%).** 문제는 그 "안 보이는" 몫이 40.3%라는 것이다. 축별로는 `가성비` 71행 중 **55행(77.5%)** 이 blind 로 가장 심하고, `분사력` 은 10행 **전부** blind 다.

> `argmaxAccuracyBlindPct = 0` 은 측정 결과가 아니라 **정의상 0**이다(키워드가 없으면 argmax 가 무매칭→오답). 지표로 읽지 말고 *"이 40%는 키워드 탐지기로는 손댈 수 없다"* 는 경계선으로 읽어야 한다.

그래서 모델 지표는 전부 `all` 과 **`blind`** 로 쪼개 냈다. 우리가 사려는 건 `blind` 쪽 성능이다.

| 지표 | 정의 |
|---|---|
| `aspectKnnP1` | 같은 `reviewId` 를 뺀 최근접 1건의 aspect 일치율 |
| `aspectQueryP1` | 축 질문 틀 평균을 프로토타입으로 둔 **14지 분류** 정답률 |
| `recallAtKMacro` | 축 프로토타입 정렬 상위 k 안의 그 축 gold 행 비율, **축별로 재서 macro 평균** (축 크기가 2~71로 편중돼 micro 는 큰 축에 끌려간다) |
| `separation` | 같은 축 쌍 평균 코사인 − 다른 축 쌍 평균 코사인 |

### 길이가 후보를 먼저 자른다

리뷰 본문 길이(글자 수, 25,000건): p50 **90** · p90 366 · p95 478 · p99 881 · max 1,468.

| 후보 | 최대 길이 | 상한 초과 리뷰 |
|---|--:|--:|
| kure · bge-m3 · (arctic-l-ko) | 8192 | **0.00%** |
| e5-base | 512 | 4.16% |
| ko-sroberta | 128 | **41.51%** |

**`ko-sroberta` 는 분리도가 가장 높은데 쓸 수 없다.** 리뷰의 41.5%가 입력 상한을 넘어 잘린다 — 그리고 잘리는 건 **긴 리뷰**, 즉 `trustPrior` 가 `contentLength` 로 높게 치는 바로 그 리뷰들이다(PER-174). 좋은 근거부터 잘라 먹는 모델을 쓸 수는 없다. 글자 수는 토큰 수의 **하한**이라 실제 초과율은 이보다 높다.

### 사례 목록 — 키워드가 전혀 못 잡는 `가성비` 4건

이슈 코멘트가 든 실제 문장이다. 정답 라벨이 없으므로 **지표가 아니라 사례 목록**이다(n=4).

| 문장 속 표현 | kure | bge-m3 | ko-sroberta | e5-base |
|---|---|---|---|---|
| "이걸 왜 **플미**주면서 사는지" | **가성비 (1위)** | 가성비 (1위) | 유분/번들거림 (2위) | 발색 (8위) |
| "**지갑터**는 한정판이네요" | **가성비 (1위)** | 가성비 (1위) | 발색 (8위) | 발색 (2위) |
| "물타입이라 너무 **헤프**네요" | 흡수력 (2위) | 흡수력 (3위) | 흡수력 (13위) | 발림감/텍스처 (6위) |
| "**날린돈**만 몇번인지" | **가성비 (1위)** | 가성비 (1위) | 트러블/자극 (2위) | 발색 (4위) |

`헤프` 는 네 모델 모두 `가성비` 를 1위로 놓지 못했다 — 같은 문장에 "흡수가 너무빨라요" 가 있어 `흡수력` 이 이긴다. **이건 모델의 실패가 아니라 한 문장이 두 축을 말한다는 증거**이고, `(리뷰 × aspect)` 가 단위인 이유(PER-175)와 같은 현상이다. kure 는 그래도 2위에 올린다.

## 5. 결정 — `KURE-v1`

**`blind` 행에서 가장 좋고, 길이 제약이 없고, 사례 4건 중 3건을 1위로 잡는다.**

- `knnP1 blind` **60.92%** · `queryP1 blind` **48.28%** — 키워드가 0%인 자리다
- `queryP1` 전체 **60.42%** 로 2위(56.94%)를 3.5%p 앞선다
- 8192 토큰이라 리뷰가 **하나도 잘리지 않는다**
- MIT 라이선스, 567M 파라미터, 한국어 검색용으로 학습된 `bge-m3` 계열

`aspectsSha256` 으로 어휘 14종을, `revision` 해시로 가중치를 못박는다. **가중치 파일이 실제로 어느 커밋의 것인지**도 리포트에 적는다 — 설정의 revision 만 믿으면 캐시가 다른 커밋을 들고 있어도 모른다.

### 기각한 후보와 사유

- **`ko-sroberta`** — 분리도 0.0849 로 1위지만 **최대 길이 128 토큰. 리뷰 41.5%가 잘린다.** 사례 4건도 전부 놓친다. *분리도가 높은 것은 짧게 잘린 문장끼리 비교했기 때문일 수 있고, 그건 우리 과제가 아니다*
- **`e5-base`** — 모든 지표에서 꼴찌. 분리도 0.0067 은 사실상 축을 못 가른다는 뜻이고, 사례 4건 모두 엉뚱한 축을 1위로 놓는다
- **`bge-m3`** — kure 와 근소한 차이(R@20 은 오히려 0.18%p 앞선다). **`blind queryP1` 은 50.00 으로 kure(48.28)보다 높다.** 그럼에도 kure 를 고른 건 `knnP1`·`queryP1` 전체와 사례 순위가 일관되게 앞서고, kure 가 `bge-m3` 에 한국어 학습을 얹은 모델이라 **같은 계열 안에서 상위 호환**이기 때문이다. 이 선택은 근소하므로 사이클 2 에서 뒤집힐 수 있다고 적어 둔다

### 재지 않은 후보 2종 — 추정하지 않는다

| 후보 | 왜 올렸나 | 왜 못 쟀나 |
|---|---|---|
| `dragonkue/BGE-m3-ko` | KURE-v1 과 **같은 베이스**에 다른 한국어 학습분. 파인튜닝 방식 차이를 가른다 | 가중치(2.2GB) 내려받기가 디스크 부족으로 실패 (`No space left on device`) |
| `dragonkue/snowflake-arctic-embed-l-v2.0-ko` | dragonkue 의 한국어 검색표에서 **1위**인 모델. 표를 낸 쪽이 자기 모델을 1위에 놓으므로 우리 데이터에서 직접 확인해야 한다 | 가중치를 받기 전에 실행이 끊겼다 (머신 종료, 2026-09-15) |

둘 다 설정에 `measured: false` + `notMeasuredReason` 으로 남긴다. **돌리지 않은 모델의 성능을 추정해 표에 넣지 않는다.** 이 둘을 재려면 리포트를 **통째로** 다시 만든다(§7).

**이 공백이 선정을 약하게 만든다는 점을 그대로 적어 둔다** — 특히 arctic 계열은 공개 표에서 1위를 주장하는 모델이다. 적용이 사이클 2 이므로 그때 재도 늦지 않지만, 재기 전까지 "우리가 후보를 다 봤다"고 말할 수 없다.

## 6. 계약 — 버전은 묶여서만 움직인다

이슈 코멘트가 완료 조건으로 추가한 원칙을 코드로 강제한다. 어휘를 클러스터링으로 만들면 **모델 교체가 주제 이름 자체를 바꾸기** 때문이다.

| 강제 | 함수 | 위반하면 |
|---|---|---|
| 벡터 레코드에 `embeddingModel`·`embeddingVersion` | `stamp_vector` / `validate_vector_record` | `EmbeddingContractError` |
| 산출물 `meta` 에 `embeddingModel`·`embeddingVersion`·**`vocabVersion`** | `stamp_meta` / `validate_meta` | `EmbeddingContractError` |
| **둘 중 하나만 바뀌는 배포 금지** | `assert_paired_bump` | `EmbeddingContractError` |
| 조합이 `releases` 에 등록돼 있어야 함 | `assert_release_registered` | `EmbeddingContractError` |
| 모델 교체는 **벡터 재생성 → 어휘 재확정 → 정답셋 재라벨링이 하나의 작업** | `plan_model_swap` / `assert_swap_complete` | 부분 교체면 `EmbeddingContractError` |

모델 ID·revision·임계값은 **코드 상수가 아니라 `pipeline/embedding_config.json`** 이다 — `trust_weights.json` 과 같은 규칙이다.

> 이건 가상의 위험이 아니다. 정답셋 v1→v2 교체에서 이미 겪었다 — 분모가 커지자 **같은 태거의 같은 산출물인데 재현율이 60.5% → 49.5%** 로 떨어졌다. 성능이 달라진 게 아니라 자가 달라진 것이다. 그래서 `goldenVersion` 까지 한 묶음(`releases`)에 넣었다.

현재 등록된 릴리스는 하나뿐이고 상태가 `selected` 다 — **벡터는 아직 만들지 않았다.**

## 7. 리포트를 `verify.sh` 에 어떻게 넣었나

`--check` 는 **모델 없이** 도는 부분만 대조한다 — 소스 sha256 · 가림률 · 키워드 기준선 · 사례 원문. 모델 수치는 가중치 수 GB 를 받아야 재현되므로 병합 게이트에 넣지 않고 **리포트 안에 실행 정체**(모델 ID · revision · 캐시된 가중치 파일의 실제 커밋)를 박는다. `measure_gate3_polarity.py` 가 태그 재생성 비용 때문에 쓰는 규칙과 같다.

**부분 갱신은 막는다.** 정답셋·키워드 사전·스냅샷이 바뀌면 `--check` 가 멈추고, 그때는 모델을 다시 돌려 리포트를 **통째로** 새로 만들어야 한다. 모델 없는 부분만 고쳐 넣으면 표의 절반이 새 데이터, 절반이 옛 데이터가 된다.

> 예외를 한 번 썼고 그 사실을 적어 둔다. 2026-09-15 실행 중단 뒤 후보 2종을 설정에 **추가**하면서 `corpusFit.byCandidate` 가 후보 목록을 따라가야 해 모델 없는 절(`source`·`corpusFit`·`keywordBaseline`·`caseList`)만 같은 함수로 다시 계산해 넣었다. 이 절들은 **어느 모델을 쟀는지와 무관하게** 결정되므로 값이 달라지지 않는다 — 실제로 바뀐 것은 `corpusFit.byCandidate` 에 두 줄이 는 것뿐이고 `models` 는 손대지 않았다. 정답셋이나 스냅샷이 바뀐 경우였다면 이 예외는 성립하지 않는다.

## 8. 기각한 대안

- **외부 임베딩 API(Voyage / OpenAI).** §1 — 계정·키·비용이 늘고 모델이 우리 통제 밖에서 바뀐다. revision 을 못박을 수 없으면 재현성이 깨진다
- **전수 태그(`v5_tags.jsonl`)를 정답으로 쓰기.** §2 — 모델 산출물로 모델을 고르면 순환이다. 태거를 잘 흉내내는 임베딩이 뽑힌다
- **이번 사이클에 게이트2 의미중복까지 붙이기.** 이슈 코멘트가 사이클 1 필수가 아니라고 정했다. 게이트2 본체는 본문 해시 + 작성자 1표로 성립한다(PER-183). 자리는 `reject_registry` 에 `duplicate_semantic` 으로 열려 있고 **쓰면 에러**다(PER-188)
- **25,000건 전수 임베딩을 미리 만들어 두기.** 모델이 바뀌면 통째로 버려진다. `releases` 가 `selected` 에 머물러 있는 이유다
- **micro 평균 R@k.** 축 크기가 2~71 로 편중돼 큰 축(`가성비` 71 · `발림감/텍스처` 68)이 평균을 끌고 간다. macro 로 냈다
- **분리도(`separation`)로 모델을 고르기.** 그 지표 1위가 `ko-sroberta` 인데 리뷰 41.5%가 잘린다(§4). 잘린 문장끼리는 서로 비슷해 보이기 쉽다
- **`argmaxAccuracyBlindPct = 0` 을 키워드의 성능으로 보고하기.** 정의상 0이라 성능이 아니다(§3)
- **재지 못한 후보 2종을 공개 벤치 점수로 표에 채우기.** §5 — 다른 데이터의 점수를 우리 표에 섞으면 표 전체를 못 믿는다

## 9. 남는 한계

- **후보 6종 중 4종만 쟀다.** 특히 `arctic-l-ko` 는 공개 한국어 검색표 1위를 주장하는 모델이다 (§5)
- **kure 와 bge-m3 의 차이가 근소하다.** `blind queryP1` 은 오히려 bge-m3 가 1.72%p 높다. 사이클 2 에서 뒤집힐 수 있다
- **정답이 432행 / 리뷰 188건이다.** 축별 행 수가 2~71 로 편중돼 있어(`탄력/탱탱함` 2 · `커버력` 9 · `향` 10) 축별 수치는 크게 흔들린다. 결론에는 전체 수치만 쓴다
- **못 잡는 축이 남는다.** kure 의 `queryP1` 이 `분사력` 0%(10행 전부 blind) · `광택/윤기` 5.56% 다. 임베딩이 키워드의 구멍을 **전부** 메우지는 않는다
- **이 probe 는 "축 분류"를 잰 것이지 "의미 유사 중복"을 잰 것이 아니다.** 게이트2 가 쓸 임계값(같은 말인지 아닌지)은 아직 정하지 않았다 — 클러스터 임계값·대표 선정 규칙은 사이클 2 의 몫이다
- **속도·메모리를 재지 않았다.** 25,000건 임베딩의 실제 소요는 사이클 2 에서 측정한다
