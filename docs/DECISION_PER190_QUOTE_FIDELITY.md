# 인용 원문성 — 사후 지표에서 생성 게이트로 (PER-190)

결정: 2026-09-15 · 코드 `pipeline/quote_gate.py` · 수치 `eval/reports/quote_fidelity_per190.json`

CLAUDE.md 서술 규칙 — *"concern의 인용문은 **원문 부분문자열이어야 한다.** v4에서
88.8%였고, 원문에 없는 수치를 생성한 사례가 있었다. 요약·재구성은 인용이 아니다."*

---

## 1. v4 가 틀린 곳은 수치가 아니라 **위치**다

v4 도 인용 원문성을 쟀다. 88.8%(127/143)라는 수가 `eval/reports/eval_report_v4.md` §5 에
있다. 문제는 그 수가 **평가 리포트에만** 있었다는 것이다. 표에는 "(참고 지표)" 라고
적혀 있고 종합 합격 산식에 들어가지 않는다.

그래서 이런 일이 실제로 일어났다.

> `클리오 _03`: 인용 "14시간 넘게 있는데 수정화장 안함" → 원본(48183818) "지속력이
> 좋으니까 수정화장도 굳이 안해도 되서 편했어요" — **"14시간"이라는 구체적 수치는
> 원문에 없음(생성 과정에서 삽입됨)**
> — `eval/reports/eval_report_v4.md` §5

수치를 알고도 막지 못했다. 사후 지표는 무엇도 막지 않기 때문이다. **PER-190 이 하는
일은 판정을 더 똑똑하게 만드는 게 아니라 판정을 생성 시점으로 옮기는 것이다.**

---

## 2. 통과 기준은 하나이고, `claim_contract` 와 같은 것이다

```
fold_invisible(quote) ⊂ fold_invisible(그 인용이 가리킨 리뷰의 원문)
```

이것은 `pipeline/claim_contract.assert_quotes_verbatim`(PER-189)이 쓰는 기준과 글자
그대로 같다. 게이트가 자기 기준을 따로 들면 **게이트를 통과한 claim 이 계약 검증에서
터진다.** 그 일치는 `pipeline/test_quote_gate.GateMatchesClaimContract` 가 7개 경계
사례로 양방향 고정한다 — 게이트가 통과시킨 것은 계약도 통과시키고, 게이트가 떨어뜨린
것은 계약도 떨어뜨린다.

---

## 3. 정규화 규칙 — 접는 것은 **보이지 않는 문자뿐**이다

`tag_contract.fold_invisible` 을 그대로 쓴다 (PER-175 결정).

| 접는다 | 근거 |
|---|---|
| `\r\n`·`\r` → `\n` | 원문 25,000건 중 46.3% 가 CRLF |
| Zs 계열 공백(U+00A0, U+3000 …) → ASCII 공백 | 1.1% |
| 폭 없는 공백 U+200B·U+FEFF 제거 | 화면에서 안 보인다 |

**글자 수와 띄어쓰기 수는 그대로 남는다.** "요약·재구성은 인용이 아니다" 는 규칙이
조금도 느슨해지지 않는다.

### 공백 전체 squeeze 는 통과 기준이 될 수 없다 — v4 는 그렇게 쟀다

```python
def _normalize(text):
    return re.sub(r"\s+", "", text or "")      # legacy/v4/eval/eval_v4.py
```

띄어쓰기를 지운 편집까지 통과시킨다. CLAUDE.md 가 명시적으로 금지하는 것이고, 실측으로
**v4 인용 143개 중 3개가 이 덕에 통과했다** (`v4.divergence.v4PassV5Fail`).

### 그래서 실패 등급을 나눈다 — 통과를 바꾸지 않고 **원인만** 가른다

파라프레이즈와 표기 차이를 구분하라는 것이 PER-190 완료 조건이다. 구분은 하되,
구분이 통과를 바꾸지는 않는다.

| 등급 | 무엇인가 | 통과 | 고칠 곳 |
|---|---|---|---|
| `verbatim` | 인용한 리뷰의 원문 부분문자열 | **O** | — |
| `linebreak_only` | 줄바꿈을 공백으로 옮겨 적은 것 외 차이 없음 | X | 표기 |
| `spacing_edited` | 띄어쓰기를 지우거나 넣어야 맞는다 | X | 표기 |
| `misattributed` | 원문이긴 한데 **다른 리뷰**의 것 | X | 근거 연결 |
| `fabricated` | 코퍼스 어디에도 없다 | X | 프롬프트 |
| `unknown_review` | 인용이 가리킨 리뷰가 코퍼스에 없다 | X | 파이프라인 |

`fabricated` 와 `misattributed` 를 한 칸에 두면 안 된다. 앞은 프롬프트 문제이고 뒤는
근거 연결 문제다 — 고치는 곳이 다르다.

### `linebreak_only` 를 통과시키지 않은 것은 **비용을 아는 선택**이다

v4 인용 3건이 여기 해당한다. 셋 다 원문에서 줄바꿈이던 자리를 공백으로 적은 것이다.

```
인용   "유수분이 비율이 적절해서 그런지 피부결이 좋아져요"
원문   "유수분이\r\n비율이 적절해서 그런지 피부결이 좋아져요"   (reviewId 44350125)
```

사람 눈에는 같은 문장이다. 그래도 통과시키지 않는다 — 통과시키려면 `fold_invisible`
자체를 넓혀야 하고, 그 함수는 **태깅 입력·중복 판정·게이트3 이 함께 쓴다.** 한 이슈에서
조용히 넓히면 다른 세 곳의 수치가 말없이 바뀐다. 넓히려면 별도 이슈에서 세 곳의
영향을 재고 `docs/DECISION_PER175_TAGGING_CONTRACT.md` 를 함께 고쳐야 한다.

## 4. 실패하면 — 인용 폐기 → 다른 근거로 대체 → 주장 폐기

PER-190 완료 조건의 순서 그대로다 (`quote_gate.enforce_evidence`).

1. **인용을 버린다.** 고치지 않는다. 가장 비슷한 원문으로 갈아끼우면 모델이 하려던
   말과 다른 문장이 근거로 남는다
2. **같은 주장의 다른 근거로 대체한다.** 대체 후보도 같은 게이트를 통과해야 하고,
   이미 쓴 리뷰는 다시 쓰지 않는다 — 한 리뷰는 한 번이다 (PER-170)
3. **`min_evidence` 를 못 채우면 주장을 버린다.** `evidence` 가 비면 `Claim` 객체는
   애초에 만들어지지 않으므로 (PER-189), `None` 을 돌려주는 것이 그 구조와 같은 말이다

결과는 `clean` · `reduced` · `substituted` · `discarded` 넷 중 하나이고, **셋 다 아닌
조용한 축소는 없다.** 폐기·대체·주장폐기가 전부 `QuoteGateResult.ledger` 행과 로그 한
줄로 남는다. `min_evidence = 0` 은 게이트를 조용히 끄는 설정이라 에러다
(`SufficiencyPolicy` 와 같은 규칙).

### `claim.rejected[]` 에는 아직 못 넣는다 — 그게 맞는 동작이다

`reject_registry`(PER-188)에 인용 원문성 사유가 등록돼 있지 않다. 미등록 사유로
`rejected[]` 행을 만들면 `assert_rejectable` 이 멈춘다. **없는 어휘를 이 이슈에서
조용히 만들지 않는다** — 만들면 게이트별 사유 분포가 거짓이 된다. 그래서 지금은
`quote_gate` 의 자기 원장과 로그에만 남기고, 등록할 항목은
`quote_gate.registry_entries()` 에 레지스트리와 같은 형식으로 적어 뒀다.

| 코드 | 게이트 | 단위 |
|---|---|---|
| `quote_not_verbatim` | `quote` | evidence |
| `quote_misattributed` | `quote` | evidence |
| `no_verbatim_evidence` | `quote` | claim |

## 5. 수치 — 무엇에 대한 몇 퍼센트인가

전부 `eval/reports/quote_fidelity_per190.json` 에 있다. **LLM 호출이 없다.**

### v4 재측정 — 88.8% 는 재현된다

| 축 | 대상 | 방식 | 결과 |
|---|---|---|---|
| A | v4 concern 인용 143개 | v4 방식 (공백 전체 squeeze + 근거 리뷰 이어붙이기) | **127/143 = 88.8%** |
| B | 같은 143개 | v5 규칙 (`fold_invisible`, 인용한 리뷰 기준) | **124/143 = 86.7%** |

리포트에 적힌 88.8%(127/143)가 **그대로 재현된다** (`axisA.reproduced: true`). 같은
입력에 v5 규칙을 걸면 86.7% 다. 차이 3건은 전부 공백 전체 squeeze 의 몫이고 목록이
`v4.divergence.v4PassV5Fail` 에 있다. 반대 방향(v5 통과·v4 탈락)은 0건 — v5 규칙은
v4 방식보다 순수하게 엄격하다.

v5 규칙의 등급 분포: `verbatim` 124 · `fabricated` 15 · `linebreak_only` 3 ·
`misattributed` 1.

**기준 코퍼스는 v4 의 500건이다** (`data/input/reviews_200_normalized.json`, 파일명과
달리 500행 — v4 평가가 쓴 파일 그대로). 25,000건 스냅샷에서 다시 재지 않았다: v4 의
500건 중 스냅샷에 있는 것은 66건뿐이라 (`corpora.overlap`) 재측정이 성립하지 않는다.

### v4 리포트를 한 곳 정정한다

v4 §5 는 불일치 16건에 대해 *"500건 전체 리뷰 원문에서 재검색해도 매칭되는 곳이
없었다"* 고 적었다. 다시 재면 **적어도 1건은 코퍼스에 그대로 있다.**

```
클리오 _07  "살짝 새틴광? 결광처럼 보여서"  → reviewId 47248041 에 정확히 존재
                                              (그 concern 의 supportingReviewIds 에는 없다)
```

파라프레이즈가 아니라 **misattribution** 이다. 고칠 곳이 프롬프트가 아니라 근거
연결이라는 뜻이고, v4 는 이 구분 자체를 하지 않았다. v4 가 왜 못 찾았는지는 재검색
절차가 코드로 남아 있지 않아 재구성할 수 없다 — **못 쟀다.**

### v5 현재분 — 100% 이고, 분모는 이것이다

| 축 | 대상 | 분모 | 결과 |
|---|---|---|---|
| C | 골든셋 라벨 전부의 인용 | 라벨 26건 · 인용 **107개** | **107/107 = 100%** |
| D | claim 으로 표현되는 라벨의 인용 | claim 22건 · 인용 **96개** | **96/96 = 100%** |
| E | D 와 같은 인용을 v4 방식으로 | 96개 | 96/96 = 100% |

D 의 96 은 `eval/reports/claim_schema_per189.json` 이 적은 96/96 과 같은 분모다.
C 와 D 의 차이 11개는 `aspect` 가 `null` 이라 claim 이 되지 못하는 라벨 4건의 인용이다
(PER-189 `conversion.notExpressible`) — 인용 자체는 C 에서 세어진다.

**이 100% 는 게이트의 효과가 아니다.** 생성기는 PER-191 이고 아직 없다. 지금 존재하는
claim 은 사람이 번들 화면을 보고 만든 골든셋 라벨의 변환분이라, 이 수가 말하는 것은
**라벨의 품질**이다. 게이트를 실제로 걸면 22건 전부 `clean` 이고 원장이 0행인데, 그건
게이트가 잘 막아서가 아니라 막을 것이 없어서다.

## 6. 남는 한계

- **게이트의 효과는 아직 못 쟀다.** 생성물이 없다 (PER-191). 지금 잰 것은 "게이트가
  올바르게 판정하는가"(테스트 30개)와 "현재분이 규칙을 만족하는가"(분모 96·107)이지
  "게이트가 무엇을 막았는가"가 아니다
- **v4 와 v5 는 코퍼스가 다르다** — 500건 대 25,000건, 겹치는 리뷰 66건. 86.7% 와
  100% 를 그대로 빼서 개선폭이라고 말할 수 없다
- **v4 산출물에는 인용별 reviewId 가 없다.** concern 단위 `supportingReviewIds` 만
  있어 v4 축에서는 misattribution 을 "근거 리뷰 목록 안에 있는가" 수준까지만 잰다.
  v5 는 인용마다 reviewId 가 있어 출처까지 판정된다 — 이건 규칙 개선이 아니라
  **스키마 개선**이고 PER-189 의 몫이다
- **`linebreak_only` 3건은 통과하지 못한 채로 남는다.** 넓히려면 `fold_invisible` 을
  쓰는 세 곳(태깅 입력·중복 판정·게이트3)의 영향을 함께 재야 한다 (§3)
- **레지스트리 미등록.** 인용 게이트의 사유가 `reject_registry` 에 없어 `rejected[]`
  행이 되지 못한다. 등록은 PER-190 의 파일 소유 범위 밖이다 (§4)
