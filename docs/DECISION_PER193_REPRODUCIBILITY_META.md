# 재현 meta — 수치가 어느 설정에서 나왔는지를 산출물이 스스로 말한다 (PER-193)

작성: 2026-09-15 · 구현 `pipeline/run_meta.py` · 테스트 `pipeline/test_run_meta.py` ·
실측 `eval/reports/meta_coverage_per193.json`

---

## 1. 범위를 meta 까지로 잘랐다

이슈 제목은 「순수함수 · 시드 · 재현 meta」였다. 2026-09-14 코멘트가 그중 하나를 뺐다.

> **09-16 범위 축소: `meta` 기록만 남긴다.**
> 남기는 것: 출력 `meta` 에 **프롬프트 버전 · 모델 ID · 임계값 · 시드 · 입력 스냅샷 해시**.
> PER-201(v4 대비 개선 귀속)의 전제라 뺄 수 없다.
> **빼는 것: 순수함수 리팩터링.** 기존 단계가 이미 `--check` 로 재실행 동일성을 확인하고
> 있으니 구조를 다시 손볼 이유가 09-16 전에는 없다.

그 판단은 실제로 맞다. `scripts/verify.sh --full` 은 재현 확인 `--check` 를 16종 돌리고
(1단 5종 + 스냅샷이 필요한 2단 11종), 계약 테스트가 그 앞에 붙는다. 재실행 동일성은
**이미 게이트에 걸려 있다.** 순수함수로 다시 쓰는 것은 같은 성질을 다른 방법으로 한 번 더
보장하는 일이고, 09-16 판정 전에 모듈 경계를 흔들면 그 판정 자체가 새 코드에 걸린다.

빠진 것은 재현성이 아니라 **귀속**이다. 같은 입력에 같은 출력이 나온다는 것과, 출력이
달라졌을 때 무엇 때문인지 아는 것은 다른 문제다. 이 이슈는 뒤쪽만 한다.

그래서 이 사이클의 산출물은 **계약과 현황까지**다. 기존 리포트를 고쳐서 빈칸을 메우지
않았다 — 메우면 "원래 있었다"가 되고, 그러면 무엇을 고쳐야 하는지가 사라진다.

## 2. 왜 meta 가 PER-201 의 전제인가

PER-201 은 "v4 대비 무엇이 좋아졌는가"를 답해야 한다. 수치가 좋아졌을 때 그게

- 임계값을 낮춰서인지 (`N_min` 8 → 5 면 통과 주장 수가 당연히 는다)
- 프롬프트를 고쳐서인지
- 모델을 바꿔서인지
- 입력 스냅샷이 커져서인지

구분할 수 없으면 "좋아졌다"는 말은 근거가 아니라 인상이다. 이 저장소는 같은 일을 이미
한 번 겪었다 — 태그 정답셋을 v1(365개)에서 v2(432개)로 다시 만든 뒤 v1 로 매긴 점수를
나란히 놓을 수 없게 됐다 (`eval/gold/README.md`, `eval/reports/gold_v1_v2_diff.md`).
**자가 달라지면 수치가 달라진다.**

## 3. 필드와 사유

`pipeline/run_meta.py` `REQUIRED_FIELDS` 12개. 축 9개 + 사무 필드 3개
(`schemaVersion` · `stage` · `unavailable`).

| 필드 | 이게 바뀌면 수치가 움직인다 | 근거 |
|---|---|---|
| `promptVersion` | 같은 모델도 다른 태그를 뱉는다. **버전 문자열 + 파일 sha256 을 함께** 박는다 — 버전만 남기면 "v1 을 고쳤는데 v1 이라 부르는" 실행이 조용히 통과한다 | `gate3_polarity_per185.json` 이 이미 `prompt.sha256` 을 박고 있다 |
| `modelId` | 태거 후보 7종이 aspect F1 에서 갈렸다 | `eval/reports/v5_tag_bedrock_bakeoff.json` |
| `policy` | `N_min`·`R_min`·`S_min` 하나만 움직여도 통과 주장 수가 달라진다 | PER-186 `sensitivity`, `SufficiencyPolicy.as_meta()` |
| `seed` | 표본·샘플링·온도가 걸린 단계는 시드 없이 같은 수가 두 번 나오지 않는다 | `context_layout_per187.json` `layouts[0].determinism.seed` |
| `inputs` | 스냅샷이 늘면 커버리지가 저절로 올라간다. 개선이 아닌데 개선처럼 보인다 | `CLAUDE.md` "새 수집분은 파일명을 바꿔 추가한다" |
| `failureTaxonomyVersion` | 실패 어휘가 바뀌면 judge 점수의 분모가 바뀐다 | `pipeline/failure_taxonomy.json` `_meta.metaField` 가 이 이름을 지정한다 |
| `embeddingModel`·`embeddingVersion`·`vocabVersion` | 벡터가 바뀌면 클러스터가 바뀌고 축이 바뀌고, 그 축으로 매긴 정답셋이 통째로 낡는다 | PER-184 계약 3조 |

임베딩 3종은 **`pipeline/embedding_contract.py` 에서 읽는다.** 같은 값을 두 군데서
정의하면 둘이 갈라지는 날이 온다 — `run_meta.embedding_fields()` 는 PER-184 의
`load_embedding_spec()` 을 그대로 부른다. `failureTaxonomyVersion` 도 코드 상수가 아니라
`failure_taxonomy.json` 에서 읽는다 (PRD §9 "정본은 설정 파일이다").

`stage` 는 축이 아니라 **어느 단계의 meta 인지**다. 태그 단계와 생성 단계가 같은
`modelId` 를 쓸 이유가 없으므로 구분이 없으면 두 meta 를 섞어 읽게 된다.

## 4. 모르는 값을 0 이나 빈 문자열로 깔지 않는다

값을 비우는 유일한 방법은 `"unavailable"` 이고, **`unavailable` 에 사유를 함께 적어야
한다.** 둘은 서로를 강제한다 — 사유 없는 `"unavailable"` 도 에러고, 사유가 있는데 값이
채워져 있어도 에러다(둘 중 하나가 낡았다는 뜻이다).

왜 이렇게까지 하는가. `0` 은 "측정했더니 0" 과 구별되지 않고, `""` 는 "아직 안 정했다" 와
"해당 없다" 를 같은 칸에 넣는다. 나중에 그 칸을 읽는 사람은 **모른다는 사실이 있었다는
것조차 모른다.** 이 저장소는 이미 세 번 같은 규칙을 썼다:

- PER-174 — 미가용 신호(`onTopic`)를 0점으로 깔지 않고 `unavailable` 에 남긴다.
  0점으로 깔면 "신호가 없다"가 "신호가 나쁘다"로 둔갑한다
- PER-172 — `renewalPolicy` 에 `null` 을 쓰지 않는다. 정하지 않았으면 `unobserved` 로
  명시하고 그 사실이 주장의 `limitation` 으로 나간다
- PER-184 — 버전이 없으면 `"unknown"` 으로 채우거나 현재 값으로 덮어쓰지 않는다.
  그러면 다른 모델로 만든 벡터가 현재 모델의 것으로 둔갑한다

같은 이유로 `_PLACEHOLDERS` 에 `""` · `"unknown"` · `"n/a"` · `"none"` · `"0"` · `"-"` 를
넣어 두고 값으로 치지 않는다. 다만 **`seed = 0` 은 진짜 시드다** — 정수 0 은 통과하고
문자열 `"0"` 은 막힌다. 자리표시자와 실제 값을 타입으로 가른다.

비울 수 **없는** 필드도 있다: `stage` · `policy` · `inputs`. 입력이 무엇인지 모르는
실행은 애초에 재현 대상이 아니고, 임계값이 없는 실행은 없다(기본값을 썼으면 그 기본값을
적는다). 이 셋을 `unavailable` 로 선언하려 하면 에러다.

## 5. 입력 스냅샷 해시 — sha256 과 커밋 해시 둘 다

이슈가 "커밋 해시로 대체 가능"이라고 적었고 실제로 `data/input/` 8개 파일이 커밋돼 있다.
둘 다 지원하되 **무엇으로 찍었는지를 `digestKind` 로 meta 에 남긴다.** 나중에 40자와
64자를 눈으로 구별하게 두지 않는다.

커밋 해시에는 조건이 하나 붙는다 — **그 경로에 대해 작업 트리가 깨끗할 때만 찍는다.**
더러운 트리에서 커밋 해시를 박으면 그 해시는 실제로 읽은 바이트를 가리키지 않는다.
재현 meta 가 거짓말을 하는 가장 쉬운 경로라 `git_commit_of()` 가 거기서 멈춘다(미추적
경로도 같다). 임시 저장소를 만들어 실제로 막히는지 테스트로 고정했다.

어느 쪽을 권하는가: **sha256 이 기본이다.** 커밋 해시는 "그 경로를 마지막으로 바꾼 커밋"
이라 브랜치마다 달라지고, 내용이 같아도 리베이스하면 값이 바뀐다. 리포트에 넣으면 재현
대조(`--check`)가 브랜치 때문에 깨진다. 커밋 해시는 사람이 이력을 되짚을 때 유용한
보조값이지 내용의 지문이 아니다.

## 6. 현황 — 계약을 통과하는 리포트는 0건이다

`eval/measure_meta_coverage.py` 가 커밋된 `eval/reports/*.json` 33건을 9축으로 훑었다
(`eval/reports/meta_coverage_per193.json`).

**이슈 리포트 13건 기준 축별 충족**

| 축 | 충족 | 비고 |
|---|---|---|
| `inputs` | 12 / 13 | 가장 잘 지켜지고 있다. 빠진 하나가 `input_contract_per176.json` |
| `policy` | 7 / 13 | 게이트 계열은 `SufficiencyPolicy.as_meta()` 를 그대로 싣는다 |
| `modelId` | 5 / 13 | `model`·`tagsModel` 도 인정해서 센 수다 |

전 리포트 33건 중 9축을 모두 충족한 것은 **0건**, 최다가 5축
(`context_layout_per187.json`)이다. `run_meta.validate()` 를 통과하는 리포트도 **0건**
이다 — `meta` 라는 자리 자체가 아직 없고, 지금은 `source` · `policy` · 최상위에 제각각
적혀 있다.

**낮게 나온 것을 이 이슈에서 메우지 않았다.** 각 리포트에 무엇을 더 적어야 하는지는
`meta_coverage_per193.json` 의 `todo.byReport` 에 목록으로 있고, 그건 각 이슈로 돌린다.

세는 방법은 **느슨한 쪽**을 골랐다: 위치를 고정하지 않고 키 이름으로 JSON 트리를 훑고,
`model`·`tagsModel` 도 `modelId` 로 인정하고, 64자 sha256 이 하나라도 있으면 `inputs` 로
인정한다. 현황을 실제보다 나쁘게 보이게 만들지 않기 위해서다 — 그렇게 세고도 낮으면
그 수치는 방법론 탓이 아니다.

## 7. 기각한 대안

**(1) 순수함수 리팩터링.** 이슈 코멘트가 잘랐다(§1). 재실행 동일성은 이미
`verify.sh --full` 의 `--check` 16종이 대조하고 있고, 09-16 판정 직전에 모듈 경계를
흔들면 판정이 새 코드에 걸린다. 귀속에 필요한 것은 구조가 아니라 기록이다.

**(2) 기존 리포트를 이 이슈에서 채우기.** 13개 리포트에 meta 를 박으면 실측이 그 자리에서
100% 가 된다. 그러면 이 이슈가 남기는 정보는 0이다 — 어느 단계가 무엇을 모르고 있었는지가
사라진다. `rejected[]` 를 드롭으로 바꾸지 않는 것(PRD §6)과 같은 이유다: *통과한 것만
남기면 정밀도는 측정되지만 재현율은 영영 측정되지 않는다.*

**(3) 리포트 파일 sha256 을 실측에 담기.** 더 촘촘한 드리프트 감지가 되지만, 다른 이슈가
자기 리포트를 고칠 때마다 `measure_meta_coverage.py --check` 가 깨져 **그 이슈의 병합
게이트를 막는다.** 축 충족과 파일 목록이 바뀔 때만 깨지게 했다 — 새 리포트가 들어오면
다시 돌려야 하고, 그건 의도한 결속이다.

**(4) 실행 시각(`generatedAt`)을 meta 에 넣기.** 넣지 않았다. 생성물에 시각이 들어가면
같은 소스에서 바이트가 달라져 재현 대조가 불가능해지고, 브랜치 간 병합 충돌이 매번 난다.
`docs/GIT_WORKFLOW.md` §3 이 이미 정한 규칙이다 — "생성기가 출력에 시각을 넣지 않고 소스
sha256 만 기록하는 이유가 이것이다". 시각이 필요하면 커밋 시각을 본다.

**(5) 열린 meta (모르는 필드 허용).** 계약을 닫았다. 열어 두면 `temperature` 처럼 수치를
움직이는 축이 누구는 적고 누구는 안 적는 상태가 되고, 그러면 축이 있는지 없는지를 매번
사람이 확인해야 한다. 축을 늘리려면 `REQUIRED_FIELDS` 와 이 문서를 함께 고친다.

**(6) 시드를 항상 요구하기.** 시드를 안 쓰는 결정적 단계(집계·대조)가 실제로 다수다.
거기에 `seed: 0` 을 박게 하면 "난수를 안 쓴다"와 "시드가 0이다"가 같은 값이 된다.
`"unavailable"` + 사유를 쓰게 했다.

## 8. 한계

- 실측은 **키 이름**으로 찾는다. 있는데 다른 이름으로 적은 것은 놓치고(`embeddingModel`
  0/13 이 그 예다 — PER-184 리포트는 `selected.model` 로 적었다), 축과 무관한 곳에 같은
  키가 있으면 과대평가한다. `foundAt` 의 경로가 그 판단의 근거로 함께 실린다
- `present` 는 "그 축을 어딘가 적었다"이지 "계약을 통과한다"가 아니다. 계약 통과는 0건이다
- 이 이슈는 계약을 **만들었을 뿐 아무 단계에도 붙이지 않았다.** 첫 사용처는 PER-191
  생성기이고, 그전까지 `run_meta.py` 는 실제 산출물을 한 건도 찍고 있지 않다
- `verify.sh` 는 이 이슈의 소유가 아니라 `measure_meta_coverage.py --check` 를 게이트에
  아직 넣지 못했다. 넣을 줄은 §9 에 적어 둔다
- 시드가 실제로 재현을 보장하는지는 검증하지 않았다. 시드를 **기록하는** 계약이지
  같은 시드로 같은 출력이 나오는지는 각 단계의 `--check` 가 본다

## 9. verify.sh 에 넣을 줄

이 이슈는 `scripts/verify.sh` 를 고칠 권한이 없다. 1단(데이터 불필요) 마지막에 넣는다 —
커밋된 JSON 만 읽으므로 `data/intermediate` 가 필요 없다.

```bash
# 리포트가 늘거나 meta 축이 바뀌면 "무엇이 아직 기록되지 않는가"가 조용히 낡는다 (PER-193)
"$PY" eval/measure_meta_coverage.py --check
```
