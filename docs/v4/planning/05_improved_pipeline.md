# 개선된 파이프라인 아키텍처 — 5단계 구조와 설계 원리

## 개요

이 문서는 DEV 피드백을 반영해 확정된 Concern Pipeline V4의 현재 구조를 설명한다. 리뷰 한 건이 어떤 단계를 거쳐 "구매 고민 질문"이 되는지, 각 단계가 LLM과 규칙(Python) 중 무엇을 쓰는지, 그리고 그 배치가 왜 그렇게 결정됐는지를 다룬다.

이 글을 읽으면 파이프라인의 전체 흐름과 세 가지 핵심 설계 원칙을 이해하고, 어느 단계에서 무엇을 바꿔야 결과가 어떻게 달라지는지 짚을 수 있다. 측면 추출을 자유 텍스트에서 enum 14종 고정으로 바꾼 배경은 [ARTICLE_enum_fixation.md](../2_DEV/ARTICLE_enum_fixation.md)에서 다룬다. 이 문서는 그 변경이 반영된 **최종 파이프라인 전체**를 설명한다.

---

## 한눈에 보는 전체 구조

5단계(Step 0~4)다. LLM은 세 단계에서만 쓰고, 나머지는 결정론적 Python 규칙이다.

```
[Step 0] 전처리 & 그룹핑              (규칙)   reviews → step0_grouped.json
    ↓
[Step 1] 리뷰별 측면 추출            (LLM)    → step1_claims.json
    ↓     aspect는 닫힌 enum 14종 중에서만
[Step 2] 측면 집계 & 클러스터링       (규칙)   → step2_clusters.json
    ↓     동의어 흡수 · MIN_SUPPORT=5 · 감성 카운트
[Step 3] 구매 고민 카테고리 분류      (LLM)    → step3_classified.json
    ↓     클러스터마다 4축(적합성/리스크/실사용/비교) 배정
[Step 4] 구매 고민 질문 생성         (LLM)    → concerns_v4.json
          클러스터당 질문 1개 + 근거 리뷰/스니펫
```

실행은 `run_pipeline.py`가 각 단계를 순서대로 호출하며, `--steps 1,2` 처럼 일부 단계만 재실행할 수 있다.

## 세 가지 설계 원칙

개선된 파이프라인을 관통하는 결정은 셋이다.

### 1. 측면은 닫힌 집합으로 고정한다

측면(aspect)은 LLM이 자유롭게 만드는 대신 **enum 14종 중 하나**만 고른다(`보습감`, `흡수력`, `트러블/자극` 등). 표준 밖 표현이 애초에 나오지 않으므로 집계 단계의 매핑 누수가 구조적으로 사라진다. 자세한 배경은 enum 고정 아티클 참고.

### 2. "무엇에 대한 말인가"와 "어떤 고민 유형인가"를 분리한다

두 개의 축을 다른 단계에서 다룬다.

| 축 | 질문 | 값 | 단계 |
|---|---|---|---|
| **aspect** | 무엇에 대한 말인가 | 닫힌 14종 | Step 1 |
| **category** | 어떤 구매 고민 유형인가 | 적합성/리스크/실사용/비교 | Step 3 |

`적합성`은 별도 측면이 아니라, 측면 + 피부 타입 힌트의 조합으로 Step 3에서 판정되는 **결과**다. 이 분리 덕에 측면 축은 단순·안정해지고, 고차 판단은 별도 단계에서 깔끔하게 표현된다.

### 3. LLM과 규칙의 역할을 명확히 나눈다

- **LLM이 잘하는 일** — 자연어 의미 해석: 측면 추출(Step 1), 고민 유형 분류(Step 3), 질문 작문(Step 4).
- **규칙이 잘하는 일** — 결정론적 집계: 그룹핑·필터·동의어 흡수·감성 카운트(Step 0, 2).

클러스터링을 LLM이 아니라 규칙으로 두면 실행마다 결과가 흔들리지 않아 평가가 재현 가능해진다.

## 단계별 상세

### Step 0 — 전처리 & 그룹핑 (규칙)

원본 리뷰를 처리하기 좋은 형태로 정비한다.

- `productKey` 기준으로 제품 5종으로 그룹핑
- 본문 30자 미만 리뷰 제외
- 별점 → `sentimentPrior` 변환 (1~2 부정 / 3 중립 / 4~5 긍정)
- 제품별 통계(건수, 평균 별점, 재구매 수) 부착

LLM 미사용. 출력: `step0_grouped.json`.

### Step 1 — 리뷰별 측면 추출 (LLM)

각 리뷰에서 언급된 측면과 감성을 구조화한다.

- 리뷰를 20건씩 배치로 묶어 호출 (모델: `claude-haiku-4-5`)
- 추출 항목: `aspect`(enum 14종 중 하나), `sentiment`, `snippet`(근거 문장 30자 이내), `skinTypeHint`(피부 타입 언급 시)
- **enum 어디에도 안 맞으면 그 claim을 생략** — 억지로 끼워 넣지 않는다
- 정보가 없거나 불확실하면 추측하지 않는다
- `reviewId` 기준 캐시로 이미 처리한 리뷰는 재호출하지 않음

출력: `step1_claims.json`.

### Step 2 — 측면 집계 & 클러스터링 (규칙)

같은 측면을 말하는 리뷰들을 묶어 빈도와 감성을 집계한다.

- Step 1이 표준 값만 내보내므로 동의어 사전(`SYNONYM_MAP`)은 **안전망**으로만 동작
- enum 외 값이 들어오면 버리지 않고 **경고 로그**를 남김 (프롬프트 이탈 모니터링)
- 측면별로 `posCount`/`negCount`/`neutralCount` 집계, `likes` 높은 순 대표 스니펫 상위 3건
- **`MIN_SUPPORT=5`**: 언급 리뷰 5건 미만 측면은 근거 부족으로 제외
- 긍·부정이 모두 2건 이상이면 `isMixed` 표시
- 정렬: mixed 우선 → 총 언급 수 내림차순

LLM 미사용. 출력: `step2_clusters.json`.

### Step 3 — 구매 고민 카테고리 분류 (LLM)

각 클러스터에 4축 카테고리를 배정한다. **제품당 1회** 호출.

- 카테고리: `적합성`(피부 타입/상황 적합) · `리스크`(자극/트러블/부작용) · `실사용`(발림감/지속성/향) · `비교`(타 제품·버전·가성비)
- 규칙 힌트: 트러블/자극은 리스크, 피부 타입 언급이 있으면 적합성 우선
- 4축 외 값이 오면 `실사용`으로 보정(안전 기본값)

출력: `step3_classified.json`.

### Step 4 — 구매 고민 질문 생성 (LLM)

클러스터를 소비자 관점의 질문으로 변환한다. **제품당 1회** 호출.

- 질문 조건: 의문형 종결, 15~60자, 구어체, 제품명 반복 금지, 광고성 표현 금지
- **부정 가능성을 열어두는 작문**: "민감한 피부에도 안전한가요?"(X) → "민감한 피부에 자극이 올 수 있나요?"(O)
- 제품당 질문 수는 클러스터 수에 따라 3~7개로 조정
- 생성된 질문에 클러스터의 근거(리뷰 ID, 긍·부정 카운트, 대표 스니펫, confidence)를 결합

출력: `output/concerns_v4.json`.

## 데이터 흐름 예시

리뷰 한 건이 질문이 되기까지를 따라가면 이렇다.

```
리뷰: "건성인데 한참 촉촉함이 유지돼요" (likes 312, ★5)

Step 0 → sentimentPrior=positive 부착, 달바 세럼 그룹에 배정
Step 1 → { aspect: "보습감", sentiment: "positive",
           snippet: "한참 촉촉함이 유지돼요", skinTypeHint: "건성" }
Step 2 → "보습감" 클러스터에 합류 (pos 41 / neg 6, 리뷰 47건 → MIN_SUPPORT 통과)
Step 3 → 피부 타입 힌트(건성) 존재 → category = "적합성"
Step 4 → "건성 피부에도 보습감이 오래 유지되나요?" + 근거 리뷰/스니펫
```

핵심은 `건성`이라는 신호가 측면 축을 오염시키지 않고 `skinTypeHint`로 보존되다가, Step 3에서 적합성 판정의 근거로 합류한다는 점이다.

## 초기 설계 대비 무엇이 좋아졌나

| 항목 | 초기 설계 | 개선된 파이프라인 |
|---|---|---|
| 측면 표현 | 자유 텍스트 → 사후 정규화 | 입력단 enum 14종 고정 |
| 미매핑 측면 | 조용히 증발 | 발생 안 함 / 발생 시 경고 로그 |
| 적합성 신호 | 측면 축에 섞임 | aspect + `skinTypeHint` 조합으로 분리 |
| 카테고리 분류 | 명시 단계 없음 | Step 3 LLM 분류로 독립 |
| 재현성 | 클러스터링 변동 우려 | 규칙 기반으로 결정론 보장 |

## 한계와 후속 과제

- **카테고리 편중**: 실행 결과 Step 3 분포가 실사용에 약 80% 쏠려 있다. 적합성·비교 축의 과소 대표 여부를 EVAL에서 점검해야 한다.
- **소수 의견 손실**: `MIN_SUPPORT=5`로 5건 미만 측면은 전부 탈락한다. 희소하지만 중요한 리스크 신호가 묻힐 수 있어 임계값 조정 여지가 있다.
- **enum 적용 범위**: 14종은 현재 제품 5종을 덮는 superset이다. 제품군이 늘면 enum 재점검이 필요하다.
- **캐시 무효화**: `--skip-cache`는 아직 수동(캐시 파일 삭제)으로 동작한다.
