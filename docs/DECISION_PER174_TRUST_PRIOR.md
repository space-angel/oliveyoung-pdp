# PER-174 — 리뷰 신뢰도 사전 점수

PRD §3-4. 모든 리뷰가 같은 무게일 수 없다. 입수 시점에 점수를 매긴다.

- 구현 `pipeline/trust.py` · 설정 `pipeline/trust_weights.json` · 테스트 `pipeline/test_trust.py`
- 근거 `eval/reports/trust_signals_per174.json` (`eval/measure_trust_signals.py` 재실행으로 재현)
- 점수 분포 `eval/reports/v5_ingest_profile.json` → `trustPrior`

---

## 0. 요약 — 무엇이 결정됐나

| 결정 | 값 |
|---|---|
| 점수의 성격 | **가중치. 필터가 아니다** — 낮아도 버리지 않고 정렬 후순위로 보낸다 |
| 범위 | `[0,1]`, 가용 신호의 가중치 합으로 정규화 |
| 채택 신호 | `contentLength` 0.6 · `uniqueContent` 0.4 · `onTopic` 0.5(입수 시점 미가용) |
| 가중치 0 | `hasPhoto` · `usagePeriod` · `likes` — **뺀 게 아니라 효과가 0과 구별되지 않았다** |
| 쓰지 않는 필드 | `usefulPoint`(정렬 점수) · `reviewerRank`/`isTopReviewer`(드롭 유지) |
| 가중치의 위치 | 코드 상수가 아니라 `pipeline/trust_weights.json` |

25K 실측 분포: min 0.1315 · p25 0.5288 · 중앙 0.623 · p75 0.7598 · max 1.0, 서로 다른 점수 **757개**.

## 1. 방향을 그대로 상수로 박지 않은 이유

PRD §3-4 는 신호 6개와 각각의 방향(↑/↓)을 제시한다. 그대로 옮기면 가중치의 근거가
"PRD 가 그렇게 썼으니까"뿐이다. 그래서 각 신호가 **실제로 근거의 양을 예측하는지** 쟀다.

정답 대리값은 **골든셋 200건의 aspect 태그 수**다 (`eval/gold/v5_tags_pilot_gold.jsonl`,
PER-175). 근거로 쓸 수 있는 문장이 몇 개 들어 있는지를 사람이 손으로 센 값이고, 이
파이프라인이 리뷰에서 실제로 뽑아 쓰는 것이 그것이다.

**한계를 먼저 적는다.** 표본 200건은 평점 층화 표본이라 코퍼스 비율이 아니고, 부트스트랩
구간이 0을 포함해도 그것은 "효과 없음"이 아니라 **"이 표본으로는 0과 구별 못 함"** 이다.
그래서 그런 신호는 삭제하지 않고 **계속 계산해 `signals` 에 남기고 가중치만 0.0** 으로 둔다.
근거가 생기면 코드가 아니라 설정 파일 한 줄을 고친다.

## 2. 신호별 판정

정답: 골든셋 aspect 태그 수 · 부트스트랩 4,000회 · 시드 20260904.

| PRD 신호 | 이 모듈 | Δ평균 태그 | 95% CI | 가중치 |
|---|---|---|---|---|
| 본문 길이 ↑(상한) | `contentLength` | **+1.31** | [+0.98, +1.64] | **0.6** |
| 동일 본문 존재 ↓↓ | `uniqueContent` | — (결정론적) | — | **0.4** |
| 배송·포장만 언급 ↓ | `onTopic` | — (태깅 후) | — | **0.5**, 입수 시점 미가용 |
| 이미지 첨부 ↑ | `hasPhoto` | +0.18 | [-0.18, +0.53] | 0.0 |
| 사용 기간 표기 ↑ | `usagePeriod` | **-0.26** | [-0.61, +0.09] | 0.0 |
| 좋아요 수 ↑ | `likes` | +0.42 | [+0.04, +0.80] → 교란 | 0.0 |

### 2-1. 본문 길이 — 유일하게 구간이 0을 배제한다

| 길이 | n | 평균 태그 | 무태그 |
|---|---|---|---|
| 0–50 | 57 | 1.11 | 21.1% |
| 50–100 | 61 | 1.46 | 14.8% |
| 100–200 | 39 | 2.26 | 7.7% |
| 200–400 | 26 | 2.69 | 0.0% |
| 400– | 17 | 3.24 | 0.0% |

100자 기준으로 무태그 비율이 **17.8% → 3.7%** 로 갈린다.

**램프 모양은 골라서 쓴 게 아니라 맞춰봤다.** 골든셋 태그 수와의 피어슨 상관:
`sqrt` **0.563** / `log` 0.556 / `linear` 0.537 / 원값 그대로 0.464.
요점은 곡선이 아니라 **상한**이다 — 상한을 두는 것만으로 0.464 → 0.537 이 오른다.
바닥 22자(코퍼스 최소), 상한 478자(p95), `sqrt` 를 채택했다.

**단, "상한"의 근거는 데이터가 아니다.** 400자 이상 구간이 여전히 가장 높아서
데이터에는 포화점이 보이지 않는다. 상한을 두는 이유는 품질 주장이 아니라
**분산 통제** — 1,468자짜리 한 건이 근거 정렬을 지배하지 않게 하려는 것이다.
그 사실을 여기 적어둔다.

### 2-2. 동일 본문 — 재지 않았다. 결정론적이라서

25K 에 동일 본문 **587그룹 / 1,433건(5.73%)**. 같은 본문이 n 개면 `1/n`. 템플릿·복붙이
근거 카운트에 n 번 들어가는 것을 막는 것이지 품질 판단이 아니므로 측정 대상이 아니다.

게이트2(PER-183)의 중복 제거와 역할이 다르다. 게이트2는 **버리고**, 여기는 **뒤로 민다**.

### 2-3. 이미지·사용 기간 — 방향을 주장할 수 없다

`hasPhoto` 는 Δ+0.18 [-0.18, +0.53]. 무태그 비율도 12.6% vs 11.0% 로 갈리지 않는다.
사진은 근거의 양과 무관하다 — 25K 의 69.1% 가 사진을 달고 있어 변별력 자체가 낮다.

`isMonthOverReview` 는 **점추정 부호가 PRD 주장과 반대다** (Δ-0.26). 구간이 0을 포함하니
"사용 기간 표기가 나쁘다"고 주장하지도 않는다. 주장할 수 있는 것은 **PRD 가 적은 ↑ 방향을
이 데이터가 지지하지 않는다**는 것뿐이고, 그래서 가중치를 0.0 으로 둔다.
(`isMonthUseReview` 는 101건 0.4% 라 애초에 신호가 되지 않는다.)

### 2-4. 좋아요 — 길이를 통제하면 사라진다

단순 비교로는 `recommendCount>0` 이 Δ+0.42 [+0.04, +0.80] 로 유의해 보인다. 그런데
좋아요는 길이와 상관이 있고(순위상관 0.310), **길이 층 안에서 다시 재면 효과가 없다.**

| 길이 층 | Δ평균 태그 | 95% CI |
|---|---|---|
| 0–100자 | +0.02 | [-0.40, +0.46] |
| 100자– | -0.13 | [-0.70, +0.42] |

좋아요는 길이의 대리값이다. `contentLength` 를 이미 0.6 으로 쓰고 있으므로 같은 신호를
두 번 세지 않는다.

## 3. `usefulPoint` 는 좋아요 수가 아니다 — 산식에 넣지 않는다

PRD 표는 좋아요 신호로 `usefulPoint` / `recommendCount` 를 함께 적었다. 둘은 같은 것이
아니고, **순위상관이 0.008** 이다. 사실상 무관한 두 값이다.

| 증거 | 값 | 의미 |
|---|---|---|
| `recommendCount` 와의 순위상관 | **0.008** | 같은 것을 재는 값이 아니다 |
| 파일 순서 단조 비증가 goodsNo | **153/153** | 크롤러가 이 값 내림차순으로 수집했다 |
| 제품별 중앙값 범위 | 8.0 ~ 396.0 (**50배**) | 제품 간 비교가 성립하지 않는다 |

두 번째가 결정적이다. 스냅샷은 제품당 상위 500건이고 그 컷의 기준이 `usefulPoint` 다 —
**표본 자체가 이 변수 위에서 잘려 있다.** 그리고 이 값은 올리브영의 자체 정렬 점수이므로,
신뢰도로 쓰면 우리가 재는 것은 리뷰의 근거력이 아니라 **올리브영의 랭킹을 그대로 다시
들여오는 것**이 된다. 이 프로젝트의 가치 주장("리뷰에서 근거를 골라낸다")과 정면으로 어긋난다.

`pipeline/test_trust.py::TestUsefulPointIsRejected` 가 이걸 테스트로 고정한다 —
`usefulPoint` 를 75480.0 으로 바꿔도 점수가 움직이지 않는다.

### 좋아요는 제품 안 백분위로 정규화한다

순수 카운트인 `recommendCount` 도 원값으로는 못 쓴다. 리뷰 나이와 교란돼 있다 —
순위상관 **-0.343**, 0인 비율이 2024년 26.9% / 2025년 33.1% 인데 **2026년은 84.7%** 다.
2026년이 코퍼스의 74.6% 다. 원값을 쓰면 리센시 컷(PER-172)으로 애써 남긴 최신 리뷰를
좋아요 신호가 바로 뒤로 밀어버린다.

그래서 `ScoringContext` 가 **제품 안 백분위**로 정규화한다. 지금 가중치가 0.0 이라
점수에 영향은 없지만, 가중치를 올리는 순간 이 교란이 되살아나지 않게 계산을 먼저 고쳐 둔다.
동점(0이 71.5%)은 같은 백분위를 받는다 — 동점을 순서로 가르면 파일 순서가 점수에 새 든다.

## 4. "배송·포장만 언급" — 입수 시점에 판정하지 않는다

PRD 는 이 신호에 "본문 판정 필요"라고 적었다. 어휘 규칙(`배송|택배|포장|박스|파손|누락|배달`)을
골든셋에 대고 재봤다.

| | 값 |
|---|---|
| 25K 중 어휘 포함 | 350건 (1.4%) |
| 정밀도 | **25.0%** (무태그 1 / 어휘 적중 4) |
| 재현율 | **4.2%** (무태그 24건 중 1건) |

**규칙이 잡으려던 것을 못 잡는다.** 골든셋에서 aspect 태그가 0개인 리뷰는 24건(12.0%)인데,
실제로 읽어보면 배송 얘기가 아니라 근거 없는 호평이다 — "부담 없이 사용하기에 괜찮아요",
"리뷰 좋길래 한번 구매해서 사용해 봤어요 아직까지는 확실한 건 모르겠지만 나름 괜찮아요".
배송·포장은 이 부류의 **좁은 특수 사례**일 뿐이다.

정확히 이 부류를 잡는 판정은 이미 파이프라인 안에 있다 — **aspect 태그가 0개인 리뷰**다.
그래서 이 신호를 어휘 규칙으로 근사하지 않고 `onTopic` 으로 두되, aspect 태깅(PER-175)
결과가 있어야 판정된다.

`onTopic` 의 가중치 0.5 는 측정값이 아니라 **정의**다. aspect 태그가 0개인 리뷰는 이
파이프라인이 쓸 근거를 하나도 담고 있지 않으므로 정렬 최하위여야 한다. 경험적 주장이
아니라 동어반복적으로 참이라서 재지 않았다.

### 미가용을 0점으로 깔지 않는다

입수 시점에 `onTopic` 은 판정할 수 없다. 이때 0점을 매기면 **"근거가 없다"와 "아직 안 쟀다"가
같은 점수**가 된다 — PER-172 에서 `renewalPolicy` 에 `null` 을 금지한 것과 같은 이유다.
그래서 **가용한 신호의 가중치 합으로만 정규화**하고, 빠진 신호를 `unavailable` 에 남긴다.

```json
"trustPrior": {
  "score": 0.5799,
  "signals": { "contentLength": 0.299854, "uniqueContent": 1.0,
               "hasPhoto": 1.0, "usagePeriod": 1.0, "likes": 0.775551 },
  "unavailable": ["onTopic"]
}
```

같은 단계 안에서는 분모가 같으므로 점수가 비교 가능하고, 단계가 다르면
`unavailable` 이 그 사실을 말한다.

## 5. `reviewerRank` · `isTopReviewer` — 드롭을 유지한다

PER-173 이 이 두 필드를 "신뢰도 산식이 등급 신호를 쓸지 미결(PER-174)"이라는 사유로
드롭했고, PER-170 이 그 결정을 이 이슈로 넘겼다. 여기서 닫는다.

**드롭을 유지한다.** 근거 두 가지.

1. **두 필드는 하나의 신호다.** `isTopReviewer` 3,070건, `reviewerRank` 존재 3,083건,
   교집합 3,070건, 등급 없는 top reviewer **0건**. 별개 신호로 세면 등급을 두 번 센다
2. **효과 구간이 0을 포함한다.** Δ+0.25 [-0.30, +0.82] (n=20). 무태그 비율은 5.0% vs
   12.8% 로 방향은 맞지만 표본이 20건이라 이 표본으로는 아무것도 주장할 수 없다

덧붙여, 등급은 **작성자에 대한 플랫폼의 평가**이지 리뷰 본문의 근거력이 아니다.
`usefulPoint` 와 같은 종류의 신호이고, 같은 이유로 신중해야 한다.

재검토 조건: 골든셋이 커져서(예: 1,000건) `isTopReviewer` 표본이 100건을 넘고 구간이
0을 배제하면, `RAW_FIELDS` 에 필드를 되살리고 `SIGNALS` 에 신호를 추가한다.

## 6. 순수 함수 — context 를 명시해서 넘긴다

`trust_prior(record, context, weights)` 는 같은 인자에 항상 같은 값을 준다 (§5-2).

중복 본문 그룹 크기와 제품별 좋아요 백분위는 리뷰 1건만 봐서는 알 수 없다. 전역 상태를
읽는 대신 `ScoringContext` 로 **명시해서 넘긴다** — 스냅샷에서 결정론적으로 만들어지므로
같은 스냅샷이면 같은 점수다. `pipeline/ingest.py` 는 레코드를 다 만든 뒤 두 번째 패스로
점수를 매긴다.

**점수와 신호 값을 함께 남긴다.** `signals` 는 가중치와 무관한 값이므로, 하위 단계가
다른 가중치를 쓰고 싶으면 입수를 다시 돌리지 않고 `rescore(signals, weights)` 만 부르면
된다. 가중치를 설정으로 둔다는 완료 조건이 실제로 작동하려면 이 분리가 필요하다.

## 7. 필터가 아니라 가중치다

점수가 0.1315(최소)여도 레코드는 그대로 남는다. 버리는 판단은 게이트(#4, PER-182~188)에서만
하고, 버릴 때는 `rejected[]` 에 사유가 남는다 — 통과한 것만 남기면 재현율을 영영 못 잰다.

점수가 쓰이는 곳은 두 군데다.
1. **근거 정렬** — 같은 주장을 받치는 리뷰 중 무엇을 먼저 보여줄지
2. **중복 게이트의 1표 선택** — PER-170 이 정한 `점수 최고 → reviewDate 최신 → reviewId 최소`.
   `trust.rank_key()` 가 이 순서를 구현한다

동점 tiebreak 가 필요한 이유는 실제로 동점이 흔하기 때문이다 — 25K 에서 서로 다른 점수가
757개뿐이다(리뷰 25,000건). 점수만으로 정렬하면 나머지는 파일 순서로 갈리고, 그러면
재현성이 파일 순서에 의존하게 된다.
