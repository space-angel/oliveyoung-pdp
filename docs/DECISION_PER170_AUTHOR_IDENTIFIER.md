# 결정 — 작성자 식별자 방침 (PER-170)

작성: 2026-09-03 · 이슈 [PER-170](https://linear.app/banjax/issue/PER-170) (블로커, due 09-04)
근거 데이터: `data/input/reviews_50products.json` (25,000건, sha256 `04e089d0…4903a773`)
근거 스크립트: [`eval/measure_author_identity.py`](../eval/measure_author_identity.py) → [`eval/reports/author_identity_per170.json`](../eval/reports/author_identity_per170.json)

> 이 문서의 모든 수치는 위 스크립트 재실행으로 재현된다. 재실행 명령은 §7.

**전제 정정 (2026-09-03).** 이 이슈는 원래 "중복 게이트 vs PII 드롭"의 충돌로 세워졌다. `userName`·`profileImageUrl`은 올리브영 프로덕션 PDP에서 리뷰만 열면 누구나 볼 수 있는 값이고, 개인정보법상 제약이 없음을 담당자가 확인했다. **따라서 충돌 자체가 없다** — 식별자는 PII 위험이 아니라 **중복 판정의 정확도만으로** 정한다. 이 문서는 그 기준으로 다시 쓴 것이다.

## 0. 결정

**작성자 식별자는 `userName` 원문이다.** 입수 스키마에 그대로 싣고, 게이트2의 "동일 작성자 1표"는 `(userName, productKey)` 단위로 적용한다. 근거 카운트는 리뷰 수가 아니라 **고유 작성자 수**를 센다.

`profileImageUrl`은 **키에 넣지 않고 감사 필드로 유지한다.** 조합키로 쓰면 식별력은 0인데 작성자 12명이 거짓 분리되기 때문이다(§4). 대신 이 필드는 "같은 이름이 정말 같은 계정인가"를 검증하는 유일한 신호이므로 스냅샷마다 재측정한다(§5 감사 규칙).

| 안 | 판정 | 한 줄 근거 |
|---|---|---|
| **`userName` 원문을 키로** | **채택** | 병합 근거를 눈으로 검증할 수 있고, 솔트·버전 관리 없이 스냅샷 간 판정이 일치한다 |
| `userName` + `profileImageUrl` 조합키 | 기각 | 식별력 **증가분 0**, 작성자 12명 거짓 분리 (§4) |
| 작성자 1표 포기 (본문 해시만) | 기각 | 잔존 오염 4,933건 = 코퍼스의 **19.7%** (§2) |
| 입수 시점 솔트 해시 | 불필요 | PII 제약이 없어 원문을 감출 이유가 없다. 게이트 로직은 키가 원문이든 해시든 동일하므로, 나중에 필요해지면 키 산출부만 교체하면 된다 |

동명이인을 구분하지 못하는 한계는 **수용한다.** 그 크기를 §3에서 실측했고, 반대 방향 오류(카운트 오염)보다 작으며 오류의 방향이 안전한 쪽(과소 계수 = 침묵)이기 때문이다.

## 1. 게이트는 실제로 필요하다 — 오염 규모

| 항목 | 실측 |
|---|---|
| 리뷰 / 고유 `userName` | 25,000 / 13,876 |
| 복수 리뷰 작성자 | 4,517명 → 해당 리뷰 15,641건 (62.6%) |
| 한 사람 최다 | 59건 |
| `(작성자, productKey)` 쌍 | 19,389개 중 **복수 3,506개** |
| 작성자 1표 미적용 시 초과 계수 | **5,611건 = 전체의 22.4%** |
| 제품별 카운트 팽창률 | 최소 6.8% / 중위 **22.9%** / p95 39.8% / 최대 **41.8%** |

팽창률 최악은 `아누아 TXA 나이아신 흔적 세럼` — 리뷰 500건이지만 고유 작성자는 291명이다. 게이트 없이 "리뷰 500건이 말한다"고 쓰면 그 문장 자체가 거짓이 된다. PRD §4-2가 지적한 카운트 오염이 이 스냅샷에 실재한다.

## 2. "작성자 1표 포기" 기각 — 본문 해시로는 대체되지 않는다

작성자 1표를 포기하고 `contentHash` 완전일치만 처리하면:

| 항목 | 실측 |
|---|---|
| 동일 본문 그룹 (코퍼스 전체) | 587종 |
| `contentHash`로 제거되는 동일제품 내 중복 | **678건** |
| 초과 표 5,611건 중 커버 | **12.1%** |
| 잔존 오염 | **4,933건 = 코퍼스의 19.7%** |

같은 사람이 같은 제품에 쓴 복수 리뷰는 대부분 **본문이 다르다** — 재구매 후 재작성, 옵션별 작성, 기간 경과 후 추가 작성. 그래서 완전일치 해시로는 잡히지 않는다.

의미 유사 클러스터링(PER-184)도 이 갭을 메우지 못한다. 같은 사람의 서로 다른 리뷰는 의미도 다를 수 있고(다른 aspect를 말한다), 반대로 다른 사람의 유사한 리뷰를 묶으면 정당한 독립 근거를 잃는다. 작성자 축과 내용 축은 서로 대체하지 않는다. **둘 다 적용한다.**

## 3. 동명이인 위험의 크기 — 수용 가능한 이유

직접 측정은 불가능하다(올리브영이 사용자 ID를 응답에 주지 않는다). 대신 **`profileImageUrl`이 이름 간 공유가 0건**이라는 실측을 이용해 "같은 계정임이 확정되는 경우"를 세고, 나머지를 위험 상한으로 잡았다.

| 항목 | 실측 | 해석 |
|---|---|---|
| 중복 쌍 3,506개 중 전 리뷰가 동일 URL 보유 | **2,403 (68.5%)** | 같은 계정 확정 → 병합이 정답 |
| URL이 서로 다른 쌍 | **0** | 동명이인 직접 증거 0건 |
| URL 없음/일부만 | 1,103 (31.5%) | 판정 불가 |
| 쌍 내부 `skinType` 상충 | **54 (1.5%)** | 동명이인 의심 신호의 상한 |
| 쌍 내부 `skinTone` 상충 | 67 (1.9%) | 같음 |

`skinType`이 상충하는 작성자 115명(복수 리뷰 작성자의 2.5%)을 따로 보면, **108명은 동일 URL로 같은 계정임이 확정**된다. 리뷰 기간 중위 18개월(최대 73개월)이므로 상충의 원인은 동명이인이 아니라 **프로필 수정**이다. 같은 달 안에서 상충한 경우는 14명 — 복수 리뷰 작성자의 **0.31%**.

> `skinType` 코드의 라벨은 PER-169 코드북(DOM 실측)을 따른다. 이 판정은 **코드 값이 같은지 다른지만** 보므로 라벨 정정(A01/A02 뒤바뀜 등)과 무관하다.

**위험 상한 1.5% (쌍 단위) vs 오염 19.7% (코퍼스 단위).** 게이트를 켜는 쪽이 13배 유리하다.

방향도 중요하다:

- **거짓 병합**(동명이인을 한 사람으로) → 근거 **과소** 계수 → 충분성 게이트에서 침묵. PRD §7-3의 FP 우선(정밀도 쪽으로 기울인다)과 같은 방향.
- **거짓 미병합**(같은 사람을 두 표로) → 근거 **과대** 계수 → "리뷰 N건이 말한다"가 거짓. §7-1 치명 2유형(근거 없는 주장 / 잘못된 귀속)에 직접 해당.

과소 계수는 보수적 실패, 과대 계수는 치명적 실패다. 상한 1.5%의 오류를 보수적 방향으로 받는 편이 맞다.

### 한계 명시 (문서화 의무)

1. `userName` 키는 **닉네임 동일성**만 보증한다. 동명이인은 한 사람으로 합쳐지고, 닉네임을 바꾼 동일인은 두 사람으로 갈라진다.
2. 위 1.5%는 **상한의 프록시**다. 31.5%(URL 없는 쌍)는 어떤 방법으로도 판정할 수 없다. "동명이인율 1.5%"가 아니라 "관측 가능한 의심 신호의 상한이 1.5%"가 정확한 문장이다.
3. 2자 이하 닉네임 896개(리뷰 1,637건)가 잠재 위험군이지만, 이들에서도 URL 상충은 0건이었다.
4. 마스킹 닉네임(`gee****` 형태) 3,733개 / 리뷰 5,602건은 원본이 이미 부분 마스킹된 값이다. 서로 다른 사람이 같은 마스킹 문자열로 수렴할 수 있으나, 마스킹+복수리뷰 977명 중 URL 상충은 **0건**이었다.

## 4. 조합키 기각 — `profileImageUrl`의 식별력 증가분은 0

| 항목 | 실측 |
|---|---|
| `profileImageUrl` 기재 리뷰 | 13,587건 (54.3%) / 고유 URL 6,187개 |
| 복수 리뷰 작성자 중 URL 보유 | 2,535명 |
| 그 중 서로 다른 URL 2개 이상 | **0명** |
| 한 URL이 여러 `userName`에 걸침 | **0건** |
| 마스킹 닉네임 중 URL 상충 | **0건** |
| 조합키를 쓰면 둘로 쪼개지는 작성자 | **12명** (일부 리뷰만 URL 보유) |

URL은 `mbrProfile/2023/07/14/1689297561721.png` 형태의 업로드 타임스탬프 경로다. 계정당 고유하지만 **한 계정 안에서 값이 갈리지도 않는다** — 즉 동명이인을 갈라줄 사례가 이 스냅샷에 한 건도 없다. 조합키는 얻는 것이 0이고 12명을 거짓 분리한다.

**필드 자체는 유지한다.** §3의 "같은 계정 확정" 판정이 이 필드에만 의존하므로, 드롭하면 동명이인 상한을 다음 스냅샷에서 다시 잴 수 없다. 키에서 빼고 감사용으로 남기는 것이 정답이다.

## 5. 규격 — 입수·게이트가 구현할 것

### 키 산출 (PER-173 입수 스키마)

```python
import unicodedata

def author_key(user_name: str) -> str:
    """작성자 키. 원문을 그대로 쓰되 유니코드 표현만 고정한다."""
    return unicodedata.normalize("NFC", user_name)
```

| 결정 | 근거 |
|---|---|
| 원문 문자열 사용 | 병합된 쌍을 사람이 열어 확인할 수 있다. 게이트2 오작동은 해시로는 디버깅이 안 된다 |
| `NFC` 정규화 | 현재 스냅샷은 NFC 아닌 이름 0건이지만, macOS 경유 재수집 시 한글 NFD가 섞이면 같은 이름이 갈라진다. 정규화를 규격에 못박아 둔다 |
| `strip().lower()` **미적용** | 적용해도 병합되는 이름 0건이다. 이득 없이 서로 다른 닉네임을 합칠 위험만 남는다 |
| 빈 값 처리 불필요 | 빈/공백 `userName` 0건 (결측 0) |
| 해시는 나중에도 가능 | 키 산출 함수 한 곳만 교체하면 게이트·카운트 로직은 그대로다. 지금 넣을 이유가 없다 |

### 게이트2 적용 규칙 (PER-183)

- 카운트 단위는 리뷰 수가 아니라 **고유 작성자 키 수**다. `support.independentReviews` = 게이트 통과한 고유 작성자 수.
- 1표를 남길 리뷰 선택은 결정적이어야 한다(§5-2 재현성): **신뢰도 사전 점수 최고 → 동점 시 `reviewDate` 최신 → 그래도 동점이면 `reviewId` 최소.**
- 탈락 리뷰는 삭제하지 않고 `rejected[]`에 `"동일작성자"`로 기록한다. 근거 드로어에는 노출하지 않되 재현율 측정에 쓴다.
- 병합 단위는 `productKey`다. 중복 쌍 3,506개 중 **428개가 서로 다른 `goodsNo`(변형 SKU)에 걸쳐 있다** — `goodsNo`로 묶으면 이 428쌍이 두 표로 남는다. 집계 단위 결정(PER-176)과 같은 방향.
- 본문 완전일치(`contentHash`)는 작성자 축과 **함께** 적용한다. 서로 대체하지 않는다(§2).

### 감사 규칙 — 동명이인 상한을 스냅샷마다 다시 잰다

- 한 `userName` 안에서 서로 다른 non-null `profileImageUrl`이 2개 이상 관측되면 **분리 후보로 플래그**하고 감사 리포트에 남긴다.
- **자동 분리는 하지 않는다.** 현 스냅샷 사례가 0건이라 검증할 수 없는 로직을 파이프라인에 넣지 않는다. 플래그가 0이 아니게 되는 순간 이 결정을 재검토한다.
- 쌍 내부 `skinType`/`skinTone` 상충(현재 1.5% / 1.9%)도 같은 리포트에 싣는다. 상한이 크게 오르면 게이트2의 병합 규칙을 다시 본다.

### 하위 영향 — 충분성 게이트

작성자 1표를 적용하면 근거 수가 줄어 침묵이 늘어난다. `productKey × skinType` 셀(미기재를 별도 세그먼트로 계산, 393개) 기준:

| | dedup 전 | dedup 후 |
|---|---|---|
| N ≥ 8 (절대하한) | 310 (78.9%) | **294 (74.8%)** |
| 셀 중위 크기 | 35 | 26 |

**16개 셀이 dedup 때문에 N_min=8을 못 넘게 된다.** 이건 손실이 아니라 원래 없던 근거였다. 제품 단위로는 50제품 전부 dedup 후에도 고유 작성자 291명 이상이라 영향이 없다.

> 이 셀 수는 데이터에 실제로 나타난 `skinType` 코드값으로 그룹핑한 결과다. PER-169 코드북이 A01~A07까지 정의하므로, 조건축 설계(PER-185)에서 쓸 때는 코드북 전체 종수 기준으로 다시 확인한다.

## 6. 인접 이슈에 넘기는 확인 사항

PER-173은 `profileImageUrl`·`reviewImages`·`reviewerRank`·`isTopReviewer`를 드롭 대상으로 두었다. 그 드롭의 근거는 **PII가 아니라 "v5 텍스트 파이프라인이 쓰지 않음"** 이므로, 쓰임이 생기면 근거가 사라진다.

- `profileImageUrl` — **유지로 변경**(§4 감사 규칙). 이 문서가 정한다.
- `reviewerRank`·`isTopReviewer` — 신뢰도 사전 점수(PER-174, PRD §3-4의 6개 신호)가 등급 신호를 쓰기로 하면 드롭과 충돌한다. **6개 신호를 확정할 때 함께 정한다** — 이 문서는 작성자 식별자만 결정한다.
- `reviewImages` — 텍스트 파이프라인 미사용이 맞다. PDP 렌더링은 별도 조회.

## 8. 입력 계약(PER-176)에 옮길 조항

> **작성자 식별자.** 작성자 키는 `NFC(userName)` 원문이다. 중복 판정 단위는 `(작성자 키, productKey)`이고 근거 카운트는 고유 작성자 키 수를 센다(`support.independentReviews`). `profileImageUrl`은 키에 포함하지 않고 감사 필드로 유지한다 — 한 이름에 서로 다른 URL이 2개 이상 나타나면 분리 후보로 플래그하되 자동 분리하지 않는다. 작성자 키는 닉네임 동일성만 보증하며 동명이인은 한 사람으로 합쳐진다 — 관측 가능한 의심 신호의 상한은 중복 쌍의 1.5%이고, 게이트를 켜지 않을 때의 카운트 오염은 코퍼스의 19.7%다 (근거: `docs/DECISION_PER170_AUTHOR_IDENTIFIER.md`).
