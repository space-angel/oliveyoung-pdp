작성: 2026-09-03 · 이슈 [PER-170](https://linear.app/banjax/issue/PER-170) (블로커, due 09-04)
근거 데이터: `data/input/reviews_50products.json` (25,000건, sha256 `04e089d0…4903a773`)
근거 스크립트: [`eval/measure_author_identity.py`](../eval/measure_author_identity.py) → [`eval/reports/author_identity_per170.json`](../eval/reports/author_identity_per170.json)

> 이 문서의 모든 수치는 위 스크립트 재실행으로 재현된다. 재실행 명령은 §7.

## 0. 결정

**옵션 1 채택 — 입수 시점 솔트 해시.** `userName`은 디스크에 원문으로 저장하지 않고, 입수 파서가 `authorHash`로 바꿔 넣는다. `profileImageUrl`은 드롭한다(옵션 2 기각). 게이트2의 "동일 작성자 1표"는 `(authorHash, productKey)` 단위로 적용한다.

```
authorHash = HMAC-SHA256(AUTHOR_HASH_SALT, NFC(userName)).hexdigest()[:16]
```

동명이인을 구분하지 못하는 한계를 **수용**한다. 그 한계의 크기를 §3에서 실측했고, 반대 방향 오류(카운트 오염)보다 작으며 오류의 방향이 안전한 쪽(과소 계수 = 침묵)이기 때문이다.

기각 사유 요약:

| 옵션 | 판정 | 한 줄 근거 |
|---|---|---|
| 1. 입수 시점 솔트 해시 | **채택** | 게이트를 유지하면서 PII를 저장하지 않는 유일한 안 |
| 2. `userName` + `profileImageUrl` 조합 | 기각 | 식별력 **증가분 0**. PII 필드가 하나 늘고 작성자 12명이 둘로 쪼개진다 (§4) |
| 3. 작성자 1표 포기 | 기각 | 잔존 오염 4,933건 = 코퍼스의 **19.7%**. 본문 해시는 초과 표의 12.1%만 잡는다 (§2) |

## 1. 게이트는 실제로 필요하다 — 오염 규모

| 항목 | 실측 |
|---|---|
| 리뷰 / 고유 `userName` | 25,000 / 13,876 |
| 복수 리뷰 작성자 | 4,517명 → 해당 리뷰 15,641건 (62.6%) |
| 한 사람 최다 | 59건 |
| `(작성자, productKey)` 쌍 | 19,389개 중 **복수 3,506개** |
| 작성자 1표 미적용 시 초과 계수 | **5,611건 = 전체의 22.4%** |
| 제품별 카운트 팽창률 | 최소 6.8% / 중위 **22.9%** / p95 39.8% / 최대 **41.8%** |

팽창률 최악은 `아누아 TXA 나이아신 흔적 세럼` — 리뷰 500건이지만 고유 작성자는 291명이다. 게이트 없이 "리뷰 500건이 말한다"고 쓰면 그 문장 자체가 거짓이 된다. PRD §4-2가 지적한 카운트 오염이 이 스냅샷에 실재한다.

## 2. 옵션 3 기각 — 본문 해시로는 대체되지 않는다

작성자 1표를 포기하고 `contentHash` 완전일치만 처리하면:

| 항목 | 실측 |
|---|---|
| 동일 본문 그룹 (코퍼스 전체) | 587종 |
| `contentHash`로 제거되는 동일제품 내 중복 | **678건** |
| 초과 표 5,611건 중 커버 | **12.1%** |
| 잔존 오염 | **4,933건 = 코퍼스의 19.7%** |

같은 사람이 같은 제품에 쓴 복수 리뷰는 대부분 **본문이 다르다** — 재구매 후 재작성, 옵션별 작성, 기간 경과 후 추가 작성. 그래서 완전일치 해시로는 잡히지 않는다. 옵션 3은 "오염을 추정해 문서화"로 끝낼 수 있는 규모가 아니라 지표 자체를 무의미하게 만드는 규모다.

의미 유사 클러스터링(PER-184)은 이 갭을 메우지 못한다. 같은 사람의 서로 다른 리뷰는 의미도 다를 수 있고(다른 aspect를 말한다), 반대로 다른 사람의 유사한 리뷰를 묶으면 정당한 독립 근거를 잃는다. 작성자 축과 내용 축은 서로 대체하지 않는다.

## 3. 동명이인 위험의 크기 — 수용 가능한 이유

직접 측정은 불가능하다(안정적 사용자 ID가 없다). 대신 **`profileImageUrl`이 이름 간 공유가 0건**이라는 실측을 이용해 "같은 계정임이 확정되는 경우"를 세고, 나머지를 위험 상한으로 잡았다.

| 항목 | 실측 | 해석 |
|---|---|---|
| 중복 쌍 3,506개 중 전 리뷰가 동일 URL 보유 | **2,403 (68.5%)** | 같은 계정 확정 → 병합이 정답 |
| URL이 서로 다른 쌍 | **0** | 동명이인 직접 증거 0건 |
| URL 없음/일부만 | 1,103 (31.5%) | 판정 불가 |
| 쌍 내부 `skinType` 상충 | **54 (1.5%)** | 동명이인 의심 신호의 상한 |
| 쌍 내부 `skinTone` 상충 | 67 (1.9%) | 같음 |

`skinType`이 상충하는 작성자 115명(복수 리뷰 작성자의 2.5%)을 따로 보면, **108명은 동일 URL로 같은 계정임이 확정**된다. 리뷰 기간 중위 18개월(최대 73개월)이므로 상충의 원인은 동명이인이 아니라 **프로필 수정**이다. 같은 달 안에서 상충한 경우는 14명 — 복수 리뷰 작성자의 **0.31%**.

**위험 상한 1.5% (쌍 단위) vs 오염 19.7% (코퍼스 단위).** 게이트를 켜는 쪽이 13배 유리하다.

방향도 중요하다:

- **거짓 병합**(동명이인을 한 사람으로) → 근거 **과소** 계수 → 충분성 게이트에서 침묵. PRD §7-3의 FP 우선(정밀도 쪽으로 기울인다)과 같은 방향.
- **거짓 미병합**(같은 사람을 두 표로) → 근거 **과대** 계수 → "리뷰 N건이 말한다"가 거짓. §7-1 치명 2유형(근거 없는 주장 / 잘못된 귀속)에 직접 해당.

과소 계수는 보수적 실패, 과대 계수는 치명적 실패다. 상한 1.5%의 오류를 보수적 방향으로 받는 편이 맞다.

### 한계 명시 (문서화 의무)

1. `authorHash`는 **닉네임 동일성**만 보증한다. 동명이인은 한 사람으로 합쳐지고, 계정을 바꾼 동일인은 두 사람으로 갈라진다.
2. 위 1.5%는 **상한의 프록시**다. 31.5%(URL 없는 쌍)는 어떤 방법으로도 판정할 수 없다. "동명이인율 1.5%"가 아니라 "관측 가능한 의심 신호의 상한이 1.5%"가 정확한 문장이다.
3. 2자 이하 닉네임 896개(리뷰 1,637건)가 잠재 위험군이지만, 이들에서도 URL 상충은 0건이었다.
4. 마스킹 닉네임(`gee****` 형태) 3,733개 / 리뷰 5,602건은 원본이 이미 부분 마스킹된 값이다. 서로 다른 사람이 같은 마스킹 문자열로 수렴할 수 있으나, 마스킹+복수리뷰 977명 중 URL 상충은 **0건**이었다.

## 4. 옵션 2 기각 — `profileImageUrl`의 식별력 증가분은 0

| 항목 | 실측 |
|---|---|
| `profileImageUrl` 기재 리뷰 | 13,587건 (54.3%) / 고유 URL 6,187개 |
| 복수 리뷰 작성자 중 URL 보유 | 2,535명 |
| 그 중 서로 다른 URL 2개 이상 | **0명** |
| 한 URL이 여러 `userName`에 걸침 | **0건** |
| 마스킹 닉네임 중 URL 상충 | **0건** |
| 조합키를 쓰면 둘로 쪼개지는 작성자 | **12명** (일부 리뷰만 URL 보유) |

URL은 `mbrProfile/2023/07/14/1689297561721.png` 형태의 업로드 타임스탬프 경로다. 계정당 고유하지만 **한 계정 안에서 값이 갈리지도 않는다** — 즉 동명이인을 갈라줄 사례가 이 스냅샷에 한 건도 없다. 얻는 것은 0이고, 잃는 것은 PII 필드 하나를 더 보관하는 위험과 작성자 12명의 거짓 분리다.

`profileImageUrl`은 **드롭한다.** 단, §3의 "같은 계정 확정" 판정에 이 필드를 썼으므로, 그 판정은 **드롭 전 스냅샷에서만 재현 가능**하다. 이 문서와 `eval/reports/author_identity_per170.json`이 그 기록이다. 향후 수집분에서 한 이름에 URL이 2개 이상 나타나면 이 결정을 재검토한다.

## 5. 규격 — 입수 파서가 구현할 것 (PER-173)

```python
import hashlib, hmac, os, unicodedata

AUTHOR_HASH_VERSION = "v5-1"          # 솔트 교체 시 올린다
_SALT = os.environb[b"AUTHOR_HASH_SALT"]   # .env — 저장소에 넣지 않는다

def author_hash(user_name: str) -> str:
    msg = unicodedata.normalize("NFC", user_name).encode("utf-8")
    return hmac.new(_SALT, msg, hashlib.sha256).hexdigest()[:16]
```

### 규격 근거

| 결정 | 근거 |
|---|---|
| HMAC + 비공개 솔트 (평문 SHA256 아님) | 닉네임 키스페이스가 작아 무솔트 해시는 사전 공격으로 역산된다. 이건 **가명화**이지 익명화가 아니다 |
| 16 hex (64비트) 절단 | 13,876개 이름에서 충돌 0건 (8·12·16·32 hex 전부 0). 64비트는 10만 이름에서도 충돌 확률 ~3e-10 |
| `NFC` 정규화 | 현재 스냅샷은 NFC 아닌 이름 0건이지만, macOS 경유 재수집 시 한글 NFD 유입이 재현성을 깨뜨린다. 정규화를 규격에 못박아 둔다 |
| `strip().lower()` **미적용** | 적용해도 병합되는 이름 0건이다. 이득 없이 서로 다른 닉네임을 합칠 위험만 남는다 |
| 솔트 고정 (수집 런 간 재사용) | 솔트가 바뀌면 스냅샷 간 `authorHash`가 달라져 중복 판정이 깨진다. 교체 시 `AUTHOR_HASH_VERSION`을 올리고 전체 재해시 |
| 제품 무관 전역 해시 | 한 작성자의 제품 횡단 행동(최다 59건)을 신뢰도 신호로 쓸 수 있게 남긴다 |

### 게이트2 적용 규칙 (PER-183)

- 카운트 단위는 리뷰 수가 아니라 **고유 `authorHash` 수**다. `support.independentReviews` = 게이트 통과한 고유 `authorHash` 수.
- 1표를 남길 리뷰 선택은 결정적이어야 한다(§5-2 재현성): **신뢰도 사전 점수 최고 → 동점 시 `reviewDate` 최신 → 그래도 동점이면 `reviewId` 최소.**
- 탈락 리뷰는 삭제하지 않고 `rejected[]`에 `"동일작성자"`로 기록한다. 근거 드로어에는 노출하지 않되 재현율 측정에 쓴다.
- 병합 단위는 `productKey`다. 중복 쌍 3,506개 중 **428개가 서로 다른 `goodsNo`(변형 SKU)에 걸쳐 있다** — `goodsNo`로 묶으면 이 428쌍이 두 표로 남는다. 집계 단위 결정(PER-176)과 같은 방향.

### 하위 영향 — 충분성 게이트

작성자 1표를 적용하면 근거 수가 줄어 침묵이 늘어난다. `productKey × skinType` 셀(미기재를 별도 세그먼트로 계산, 393개) 기준:

| | dedup 전 | dedup 후 |
|---|---|---|
| N ≥ 8 (절대하한) | 310 (78.9%) | **294 (74.8%)** |
| 셀 중위 크기 | 35 | 26 |

**16개 셀이 dedup 때문에 N_min=8을 못 넘게 된다.** 이건 손실이 아니라 원래 없던 근거였다. 제품 단위로는 50제품 전부 dedup 후에도 고유 작성자 291명 이상이라 영향이 없다.

## 6. 남은 PII 처리 — 이 결정이 자동으로 해결하지 않는 것

`authorHash`는 **v5 입수 이후**를 규율한다. 이미 커밋된 원본 스냅샷 3개에는 `userName`·`profileImageUrl`·`reviewImages`가 남아 있다.

| 파일 | 상태 |
|---|---|
| `data/input/reviews_50products.json` | 25,000건, PII 3필드 포함. 커밋됨 (`9ea3ade`) |
| `data/input/reviews_200_normalized.json` | 500건, 동일 |
| `data/input/v4_reviews_500.json` | 500건, 동일 |

따라서:

1. **v5 파이프라인은 원본을 직접 읽지 않는다.** 입수 단계가 비식별 파생본(`data/input/reviews_50products_v5.json`)을 만들고, step0 이후는 그것만 입력으로 받는다. 파생본에 PII 필드가 남아 있으면 **에러**를 낸다(조용한 폴백 금지 — PER-176).
2. 원본 3개는 `data/input/` read-only 규칙에 따라 **그대로 둔다**. 재현 근거이고, §3·§4의 판정이 이 파일들에만 존재한다.
3. 그래서 **이 저장소는 비공개 유지가 전제다.** 원격 공개로 전환할 때는 파일 삭제만으로 부족하고 `9ea3ade`를 포함한 **히스토리 재작성**이 필요하다. 공개 전환은 별도 이슈로 다룬다.
4. 새 수집분은 크롤러가 **원문 `userName`을 디스크에 쓰지 않고** 해시로 저장한다. 그 시점부터 1~3의 부채가 늘지 않는다.

v4 파이프라인 코드에는 `userName`·`profileImageUrl`·`reviewImages` 참조가 **0건**이다(`grep` 확인). 즉 PII는 입력 스냅샷에만 있고 중간·최종 산출물로 전파된 적이 없다.

### 인접 이슈에 넘기는 확인 사항

PER-173은 `reviewerRank`·`isTopReviewer`도 드롭 대상으로 두었다. 신뢰도 사전 점수(PER-174, PRD §3-4의 6개 신호)가 등급 신호를 쓰기로 하면 그 드롭 목록과 충돌한다. **어느 쪽이 맞는지는 PER-174에서 6개 신호를 확정할 때 함께 정한다** — 이 문서는 작성자 식별자만 결정한다.

## 8. 입력 계약(PER-176)에 옮길 조항

> **작성자 식별자.** 입수 파서는 `userName`을 저장하지 않는다. `authorHash = HMAC-SHA256(AUTHOR_HASH_SALT, NFC(userName))[:16]`(버전 `v5-1`)만 저장한다. `profileImageUrl`·`reviewImages`는 드롭한다. 중복 판정 단위는 `(authorHash, productKey)`이고 카운트는 고유 `authorHash` 수를 센다. `authorHash`는 닉네임 동일성만 보증하며 동명이인은 한 사람으로 합쳐진다 — 관측 가능한 의심 신호의 상한은 중복 쌍의 1.5%이고, 게이트를 켜지 않을 때의 카운트 오염은 코퍼스의 19.7%다 (근거: `docs/DECISION_PER170_AUTHOR_IDENTIFIER.md`). PII 필드가 남은 입력이 들어오면 파이프라인은 에러를 낸다.
