## 1. 단위가 리뷰면 정보를 잃는다

리뷰 하나에 감성 하나를 붙이면 "발색은 예쁜데 지속력은 별로"를 표현할 수 없다. 파일럿
200건 실측:

```
한 리뷰 안에서 방향이 갈린 비율     20.5%  (36 / 176)
별점과 태그 방향이 불일치한 태그     12.9%  (47 / 365)
★5 리뷰 60건에서 나온 부정 태그      13개
```

별점을 방향의 대리값으로 쓰면 저 13개가 전부 긍정으로 뒤집힌다. 그래서 단위는
`(리뷰 × aspect)`이고, polarity는 **그 문장이 말한 방향**이지 리뷰 전체의 인상이 아니다.

별점 불일치는 오류가 아니라 **게이트3이 잡아야 할 플래그**다. 리포트에서도 오류로 세지 않는다.

### 같은 aspect를 두 번 넣지 않는 이유

한 aspect 안에서 방향이 갈리면(예: "발색력은 좋은데 노란기가 아쉽다") 서로 다른 aspect로
나누고, 나눌 수 없으면 그 태그를 만들지 않는다.

중복을 허용하면 집계에서 같은 리뷰가 같은 주제에 찬반 양표를 던져 방향이 흐려진다.
비용은 실측했다 — 표본에서 이 규칙 때문에 한쪽을 버린 사례는 소수이고(`reviewId 63358864`
등), **버린 사실이 리포트에 남는다.** 빈도가 올라가면 택소노미 해상도 문제로 재검토한다.

## 2. `skinTypeHint`는 코드로 받는다 — v4가 실패한 지점

v4는 힌트를 라벨 문자열("건성")로 받았다. 조건축은 코드(`A02`)라서, 집계 단계에서 둘이
만나지 못하고 힌트가 통째로 유실됐다. **카테고리 분포 FAIL의 원인이다.**

v5는 코드로 받고, 코드북 밖의 값이면 에러다.

```
A01 지성 · A02 건성 · A03 복합성 · A04 민감성 · A05 약건성 · A06 트러블성 · A07 중성
```

### 힌트가 실제로 늘리는 몫

| | 건수 (표본 200) |
|---|---|
| 본문에서 피부타입을 밝힌 리뷰 | 28 |
| 그중 `condition.skinType`이 미기재 → **조건축 순증** | **9** |
| 프로필과 **불일치** | **6** |
| 프로필과 일치 | 13 |

### 불일치를 자동으로 해소하지 않는다

불일치 6건은 프로필 등록값과 이번 리뷰의 자기 진술이 다른 경우다(예: `reviewId 32320525`
프로필 `A02` · 본문 "전 복합이긴 한데" → `A03`).

**어느 쪽이 참인지 정할 근거가 없다.** 프로필은 오래 전 등록값일 수 있고, 본문 진술은
그날의 컨디션일 수 있다. 자동 우선순위를 정하면 그 선택이 어디에도 안 남는다. 그래서
**플래그만 남기고 게이트 단계에서 규칙을 정한다.**

### 본인 진술만 힌트다

"건성용으로 좋아요", "지성이 여름에 쓰기 좋아요"는 힌트가 아니다 — 제품이 누구에게 맞는지에
대한 진술이지 작성자의 피부가 아니다. 이걸 힌트로 받으면 세그먼트가 오염된다.

## 3. 인용 — 보이지 않는 문자만 접는다

`CLAUDE.md`: *인용문은 원문 부분문자열이어야 한다. 요약·재구성은 인용이 아니다.*
v4는 88.8%였다.

### 원문에 보이지 않는 문자가 섞여 있다 (25K 실측)

```
개행이 \r\n 인 리뷰            11,582건 (46.3%)
Zs 계열 공백 변종 포함 리뷰        268건 ( 1.1%)
  U+00A0 NO-BREAK SPACE, U+3000 IDEOGRAPHIC SPACE 등
폭 없는 공백 U+200B / U+FEFF      리뷰 96건
```

태거가 화면에서 본 대로 정확히 복사해도 바이트가 안 맞는다. 파일럿에서 실제로 **첫 50개 중
3개가 이 이유로 탈락**했다. v4의 88.8%에 이 몫이 섞여 있었을 가능성이 높다.

### 규칙

태거에게 주는 본문과 대조하는 본문 **양쪽에 같은 접기**를 적용한다 (`tag_contract.fold_invisible`).

```
\r\n · \r        →  \n
Zs 계열 공백      →  ASCII 공백
U+200B · U+FEFF  →  제거
U+200D (ZWJ)     →  건드리지 않는다 (이모지 결합에 쓰인다)
```

**접는 것은 보이지 않는 문자뿐이고 글자·띄어쓰기 수는 그대로다.** 재구성·요약·띄어쓰기
변경은 여전히 탈락한다.

### 공백 전체 squeeze를 기각한 이유

`"발색은정말예쁜데"`처럼 띄어쓰기를 지운 것까지 통과시킨다. 그건 복사가 아니라 편집이다.
`raw.content` 자체는 고치지 않는다 — 원문층은 무가공이고, 접기는 태깅 입력과 대조에만 쓰는
파생 뷰다.

### 중복 판정(게이트2)에는 이 정규화가 필요 없다

같은 정규화를 `contentHash`에 적용해도 **증가분이 정확히 0**이다. CRLF가 46.3%에 있지만
일관되게 들어가 있어서 "같은 본문인데 줄바꿈만 다른 쌍"이 이 스냅샷에 없다.

| 해싱 전 정규화 | 중복 그룹 | 초과 표 |
|---|---|---|
| 현재 (strip만) | 587 | 846 |
| 보이지 않는 문자만 접기 | **587** | **846** |
| 공백 전부 제거 | 621 | 885 |
| 공백 1개로 접기 | 619 | 882 |

squeeze는 초과 표 5,611건의 0.6~0.7%를 더 잡지만 "띄어쓰기만 다른 서로 다른 리뷰"를
병합할 위험을 진다. → **`contentHash` 규격 유지.** 두 곳의 규칙이 다른 이유가 이것이다.

## 4. 택소노미 14종은 동결한다

v4가 쓴 14종을 그대로 승계한다. **PER-201 v4 대비 비교의 축**이라, 바꾸면 개선분이
택소노미 변경 때문인지 파이프라인 때문인지 귀속이 안 된다.

동결하되 **비용은 기록한다.** 파일럿 실측:

```
상위 6종이 74.0% 점유
분사력 0회 · 탄력/탱탱함 3 · 광택/윤기 5 · 커버력 10 · 향 10
침묵 24건 중 택소노미에 칸이 없어서인 것 5건 (피부결·모공×2·맛·용기 파손)
태그를 붙인 리뷰 안에서도 주름·속눈썹 길이/컬링은 갈 곳이 없어 버려짐
```

**14종은 스킨케어 편향이고 색조·아이/립에서 구멍이 난다.** 확장은 별도 이슈에서 근거를 대고
한다 — 이 문서를 고치고 사유를 남기는 것이 그 절차다.

## 5. 전수 25,000건 — 리센시 컷으로 미리 거르지 않는다

리센시 컷(`policy.RECENCY_CUTOFF_MONTH` = `2024-09`) 통과분 22,194건만 태깅하면 11.2%,
**$1.27**을 아낀다 (`$11.29 × 0.112`). 기각한다.

- 컷 값은 셀 손실 −10으로 정한 값이고 **PER-200 커버리지 측정 뒤 조정될 수 있다.** 미리
  걸러 태깅하면 컷을 바꾸는 순간 재태깅이다
- 컷이 "게이트 판정"이 아니라 "입력에서 빠진 것"이 되면 `rejected[]` 회계가 깨진다.
  버린 리뷰가 무슨 aspect를 말했는지 모르면 **재현율을 영영 못 잰다** (§6)

컷을 되돌릴 수 있게 유지하는 값이 $1.27보다 크다.

## 6. 채점 — 정답셋의 키는 `reviewId`뿐이다

정답셋 행에 `productId`를 넣지 않는다. 리뉴얼 세대가 갈리면(PER-172) 같은 `goodsNo`의
`productId`가 날짜에 따라 나뉘어 키가 깨진다. 채점은 `(reviewId, aspect)`로만 대조한다.

```bash
python3 eval/validate_tags.py --tags <배치결과> --against eval/gold/v5_tags_pilot_gold.jsonl
```

전체 365개(태거 성능)와 게이트1 통과분 300개(실제로 주장에 쓰이는 태그의 성능)를 **둘 다** 낸다.

## 7. 한계

- 정답셋은 **Opus 5가 만들었고 사람이 재검토하지 않았다.** 배치(Haiku 4.5)와의 일치율은
  "정답 대비 정확도"가 아니라 "더 큰 모델과의 합치도"로 읽어야 한다
- 표본 200건은 층화 추출이라 **표본 비율을 코퍼스 비율로 읽으면 안 된다.** 코퍼스 수치는
  `corpusEstimate`의 가중치로 되돌린 추정이다
- 리뷰당 태그 상한 5는 장문에서 실제로 정보를 자른다(상한에 닿은 8건이 전부 400자 이상).
  지금은 유지하고, 상향 시 출력 토큰이 함께 오른다
- 비용 재계산의 시스템 프롬프트 토큰(829 → 1,139)은 **문자수 비례 추정**이다.
  배치 실행 전 `count_tokens`로 재야 한다
