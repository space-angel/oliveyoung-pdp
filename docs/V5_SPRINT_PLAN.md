## 0. 먼저 — PRD 요구사항의 실행 가능성 실측

설계 전에 PRD가 이 데이터(25,000건)에서 성립하는지 확인했다. 세 개는 성립하고, 네 개는 조건이 붙는다.

### 0-1. 비용은 병목이 아니다

step1 전수 태깅을 `count_tokens`로 실측했다. 배치 20건당 입력 5,693토큰(시스템프롬프트 829 고정), v4 실측 리뷰당 1.65클레임 기준 출력 2,100토큰.

| 25,000건 / 1,250배치 | 표준 | Batch API(50%) | +프롬프트 캐싱 | 둘 다 |
|---|---|---|---|---|
| Haiku 4.5 | $20.24 | $10.12 | $19.31 | **$9.65** |
| Sonnet 5 | $40.48 | $20.24 | $38.61 | $19.31 |

입력 7.12M · 출력 2.62M 토큰. step3·step4는 클러스터 단위라 훨씬 작다 — **비용의 대부분이 step1이고, 그게 $20 이하다.** 전수 실행을 아낄 이유가 없다.

### 0-2. 조건부 진실(§3-2)은 상위 aspect에서만 성립한다 — 이게 이 프로젝트의 핵심 실험

PRD의 가장 큰 설계 주장은 "조건을 붙이면 상충 리뷰가 모순이 아니라 세그먼트 차이로 정리된다"다. 실측:

```
condition 필드 결측률
  skinType    57.1% 만 값 있음   (10,723건 미기재)
  skinTone    54.8%
  skinTrouble 53.9%
  option      68.1%
  usagePeriod  필드 자체가 없음 — isMonthOverReview 불리언 9,593건이 유일한 근사

productKey × skinType 셀 (343개)
  크기 min=1 / median=28 / max=186
  8건 이상  260개 (75.8%)   ← §4-4 절대하한 N_min=8 기준
  15건 이상 218개 (63.6%)
  30건 이상 166개 (48.4%)

여기에 aspect까지 교차하면
  v4가 뽑은 aspect 14종, 상위 6종이 71% 점유
  제품당 500건 × 1.65클레임 / 14 aspect = aspect당 59클레임
  × skinType 기재율 57% / 4분할 = 셀당 약 8.4클레임  ← N_min=8 경계
```

**판정: 조건부 주장은 상위 aspect에서 겨우 성립하고, 롱테일 aspect에서는 절대하한을 못 넘어 침묵해야 한다.**

이건 설계 실패가 아니다 — PRD §4-4가 "리뷰가 적은 제품은 주장을 적게 보여주거나 아무것도 안 보여준다"고 이미 정한 동작이다. 다만 **조건부 주장이 실제로 몇 개 살아남는지(커버리지)가 가정이 아니라 측정 대상**이라는 뜻이다. 이걸 별도 이슈로 세운다.

### 0-3. 게이트 2(중복)는 실제로 필요하다

```
고유 userName 13,876 / 복수 리뷰 작성자 4,517명 → 해당 리뷰 15,641건 (62.6%)
최다 작성자 59건 (lulululalalah), 46건, 37건…
같은 제품에 복수 리뷰를 쓴 (작성자, 제품) 쌍 3,506개
동일 본문 중복 587종
```

§4-2의 "동일 작성자 복수 리뷰 → 1표"가 없으면 "리뷰 N건이 말한다"는 숫자가 실제로 오염된다. **단, 안정적 사용자 ID 필드가 없다** — `userName` 문자열이 유일하고 동명이인을 구분할 수 없다. → **작성자 키 = `NFC(userName)` 원문으로 확정** (PER-170, §3 블로커 표 참조). 당초 걸림돌이던 PII 드롭 논점은 프로덕션 공개 값 확인으로 해소됐다.

### 0-4. PRD가 요구하지만 이 프로젝트에서 불가능한 것

| PRD | 요구 | 왜 불가능한가 |
|---|---|---|
| §0_2 | 성공을 **행동 지표**로 정의 (이탈 없이 결정까지 간 비율, 근거 리뷰까지 읽은 비율) | 미출시 PoC. 트래픽 0 |
| §11-9 | A/B | 같은 이유 |
| §11-8 | 하드 샘플 저장소 + 퓨샷 리트리빙 | 소스가 "운영에서 나온 실패"인데 운영이 없다 |
| §4-2 | 의미 유사 임베딩 클러스터링 | **Anthropic API에 임베딩이 없다.** 별도 제공자 또는 로컬 모델 결정 필요 |
| §3-1 | `usagePeriod` (1주/1개월/6개월) | 데이터에 없다. 본문 LLM 추출 아니면 스코프 제외 |
| §3-2 | `skinType` 조건 표기 | 코드(A01~A04)만 있고 **라벨 사전을 API에서 못 받았다** (`data/input/skin_codes_probe_result.json`) |

§0_2가 특히 중요하다. PRD가 "모델 지표는 부지표일 뿐, 행동 지표가 안 움직이면 부지표는 버리는 게 맞다"고 못 박았으므로, **PRD 자신의 기준으로는 이 프로젝트가 성공을 증명할 수 없다.** 대리 측정을 스프린트에 명시적으로 넣어야 방어가 된다. 두잇투게더에서 12명 세션으로 가설을 판정한 선례가 있다.

## 1. 스프린트 체계

Build 팀(PER)은 현재 Cycle을 쓰지 않는다. **1주 Cycle 4개**를 켜고, 마일스톤은 시간이 아니라 **산출물 경계**로 쓴다.

```
Cycle 1   09-03(수) ~ 09-09(화)    데이터 계약 + 평가 기준 착수
Cycle 2   09-10(수) ~ 09-16(화)    게이트 + 생성 + 자동평가 → 판정
Cycle 3   09-17(수) ~ 09-23(화)    화면 설계 + 통합
Cycle 4   09-24(수) ~ 09-28(월)    검증 + 케이스 문서화
```

**Cycle 2 끝(09-16)에 평가된 결과가 나와야 한다.** 병렬 프로젝트 'PM 포트폴리오 제작'의 C1b 문장화 마감이 09-20이고, 문장화에는 판정된 수치가 필요하다. 여기가 이 일정의 실질 데드라인이며, Cycle 3·4는 그 뒤 작업이다.

### 왜 마일스톤이 아니라 Cycle을 같이 쓰나

마일스톤만 쓰면 "무엇이 완성됐나"는 보이지만 "이번 주에 무엇을 포기했나"가 남지 않는다. PRD §11이 의존성 순서를 못 박아둔 만큼 **주 경계마다 스코프를 잘라내는 결정**이 반드시 생기고, 그 결정 이력이 #9 케이스 문서화의 재료다. Cycle 단위 완료/미완료가 그걸 자동으로 남긴다.
